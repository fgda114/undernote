## 0. 설계 원칙 3개 — 모든 기능이 이 셋을 통과해야 한다

1. **원의 입력은 편집 판단뿐이다.** 평론 1편 발행에 원이 제공하는 것은
   글 + 4개 필드(앨범·아티스트 / 장르 버킷 / 점수 / 발매일 확인)가 전부다.
   그 외 전부 — 메타데이터 조회, 커버 아트, 링크 생성, 리스트 갱신, 배포 —
   는 시스템 또는 User의 일이다. (charter §6: "원이 글쓰기 외에 아무것도 안
   해도 되는가")
2. **리스트는 조립하지 않는다. 도출한다.** 노미네이트·10선·월말정산은 전부
   평론 메타데이터에서 빌드 타임에 자동 생성된다. 사람이 리스트를 따로
   관리하는 순간 USP-A의 "평론 = 리스트 작업" 등식과 100% 연결 불변식이
   깨진다. (usp.md §1)
3. **지금은 완전히 닫는다.** 계정·DB·댓글 대비 설계 금지. 남기는 것은
   "콘텐츠의 구조화 저장"(이식 가능성) 하나다. (charter §5 확정 사항)

## 1. 핵심 결정 D1~D9

리드가 지정한 결정 과제 ①~⑤를 포함한다. **D1의 버킷 구성은 원의 결정
대상**이며 선택지는 `open-decisions.md`에 있다. 나머지는 기획 확정이다.

### D1. 장르는 두 층위다 — 리스트 버킷(원 결정) + 세부 장르 태그(자유)

**v1.1 개정.** 원의 추가 답변("생소한 장르들을 대중들에게 쉽게 설명" ·
"장르의 역사와 유행하는 장르들을 소개")으로 장르의 용도가 둘임이 드러났다.
**하나의 분류 체계로 묶지 않는다:**

| 층위 | 용도 | 성질 | 개수 |
|---|---|---|---|
| **① 리스트 버킷** | 노미네이트 5 → 선정 1의 칸. 연간 부담을 결정 | 굵다 · 고정적(연 단위 설정) · 평론당 **택1 필수** | **적어야 한다** — 원 결정 (아래 표) |
| **② 세부 장르 태그** | "생소한 장르 설명"의 소재 축 · 계보/사다리 연결의 정밀 키 | 세밀 · 자유 어휘 · **복수 · 옵션** | 제한 없음 — 생소할수록 콘텐츠 가치 |

- 버킷을 세밀하게 쪼개면 노미네이트 빈칸이 생기고, 설명 대상을 굵게 묶으면
  "생소한 장르"라는 소재가 죽는다 — 분리가 유일한 해법이다.
- **세부 태그는 옵션이므로 D7 상한(원의 접점)을 늘리지 않는다.** 안 달아도
  모든 기능이 성립하고, 달면 사다리(D6-2)가 정밀해진다.
- 세부 태그는 **표기 등록부로 정규화**한다("인디 록" vs "indie-rock" 문제 —
  John의 미확인 항목에 대한 기획 답). 등록부는 데이터이며 User가 관리한다.
- 음악 이야기에도 세부 태그가 붙는다 — "이 장르가 어디서 와서 지금 뭐가
  유행인가"를 쓰는 글의 앵커 (D9 · charter §7.5).

**리스트 버킷 구성 — 원 결정 대상 (기획 추천: 3버킷).**
결정 기준은 음악학이 아니라 집필 가능성이다. 버킷 1칸 = 연간 노미네이트
5칸 = 평론 5편의 약속이다.

| 안 | 버킷 구성 | 노미네이트 칸 | 연간 평론 하한 | 월 환산 |
|---|---|---|---|---|
| A | 힙합/R&B · 팝 (2개) | 10 | ~10편 | ~0.8편 |
| **B (추천)** | **힙합/R&B · 팝 · 록 (3개)** | **15** | **~15편** | **~1.3편** |
| C | 힙합 · R&B · 팝 · 록 (4개) | 20 | ~20편 | ~1.7편 |

- 하한 산정: 노미네이트 = 평론이 있어야 하는 앨범 (charter §1). **10선은
  추가 부담 없음** — D3 참조.
- 추천 근거: 원의 레퍼런스 3종 중 2종이 힙합/흑인음악, 예시도 전부 힙합
  (charter §7.5)이며 록·팝 언급 실재 (리드 확인). C안의 R&B 단독 분리는
  "R&B만으로 5장" 가능성이 미확인이라 리스크가 크다.
- **버킷 목록은 연 단위 설정값이다.** 이듬해 추가·축소 가능해야 한다
  (데이터 모델 요구 → §5).
- **"그 외" 처리:** 버킷 밖의 앨범도 평론할 수 있다(버킷 = "그 외").
  장르별 보드에는 안 오르지만 10선 후보와 아카이브에는 포함된다.
  세부 태그는 그대로 달 수 있으므로 **버킷이 좁아도 다룰 수 있는 음악의
  폭은 줄지 않는다.**
- **연말 장르 리스트 성립 규칙(제안):** 연말 시점 해당 버킷 평론이 2편
  이하면 그 해 그 버킷 리스트는 발행하지 않는다. 3~4편이면 정원 미달인
  채로 발행한다. 5는 정원이지 최소가 아니다. — charter §1 트레이드오프의 구체화.

### D2. 점수 표시 방식 — 확정 (리드 지정 과제 ②)

점수제 자체는 charter 확정(10점 만점 소수점, 비협상). 결정한 것은 배치다.
Caleb의 두 발견 — "레퍼런스 누구도 점수로 신뢰를 얻지 않았다", "선별 매체는
점수 분포 압축으로 소수점이 구조적 필연" — 을 그대로 규칙으로 만든다:

| 지면 | 점수 | 근거 |
|---|---|---|
| **리스트 지면** (10선·보드·월말정산) | **표시 + 점수 내림차순 정렬** | 점수의 존재 이유 = 줄 세우기 (charter §1). 순위는 근거를 보여야 한다 |
| **평론 페이지** | **글 말미(맺음 블록)에 표기.** 상단 히어로는 앨범·아티스트·장르·발매일만 | 점수는 결론이지 간판이 아니다. 논증을 읽고 판결에 도달하는 순서 |
| **탐색 지면** (아카이브·최신 글 목록·아티스트 페이지) | **비표시** | 탐색은 글로 고르게 한다. 점수 소비는 리스트 지면이 전담 |

- **소수점 1자리 고정** (예: 8.3). 2자리는 거짓 정밀도다. 1자리로 100단계 —
  선별 매체의 압축된 분포에서 변별에 충분하다.
- 점수 척도의 의미(몇 점이 무엇인가)는 **정의하지 않는다.** 그것은 원의
  편집 척도이고, 일관성은 규칙이 아니라 축적으로 증명된다 (신뢰 경로 ②).
- 지면 내 정확한 시각 배치는 Jonnathan 재량 (§6 전달).

### D3. 올해의 앨범 10선의 후보 풀 — 확정

charter §1이 W2로 넘긴 미확정("풀 밖에서 뽑는가")에 답한다:

> **10선 = 그해 발매 앨범 중 평론이 발행된 전체에서 점수 상위 10.**
> 버킷 노미네이트 여부와 무관하다 ("그 외" 버킷 포함).

- 추가 집필 부담 0 — 모든 후보에 평론이 이미 있다 (평론 없는 앨범은
  정의상 후보가 아니다). charter §1 역산표의 하한이 그대로 최종 하한이 된다.
- 버킷 체계(D1)와 10선이 분리되므로, 버킷 밖 걸작이 10선에서 누락되는
  구조적 결함을 원천 차단한다.

### D4. 노미네이트 도출 방식 — 자동 (원 확인 대상)

> **버킷별 노미네이트 5 = 그 버킷 그해 발매작 평론 중 점수 상위 5.
> 버킷 선정 1 = 그중 1위. 원의 별도 지정 행위 없음.**

- 근거: 점수가 곧 원의 편집 판단이다. 점수와 별개의 "후보 지정"을 두면
  ① 원의 관리 노동이 생기고(원칙 0-1 위반) ② 점수 순위와 후보가 어긋나는
  순간 "왜 점수 높은 저 앨범은 후보가 아닌가"에 답할 수 없게 된다 —
  리스트 권위의 자해다 (charter §1 신뢰 논리).
- 동점 처리: 평론 발행일 이른 순 (더 오래 검증대에 있었던 쪽). 빌드가
  상위권 동점을 감지하면 원에게 알린다 — 소수점 조정으로 원이 직접
  가를 수 있다 (강제 아님) → `SS-3`
- 연중 전이: 새 평론이 기존 5위 점수를 넘으면 보드가 자동 교체된다.
  이 교체 자체가 연중 콘텐츠다("○○가 보드에 진입").
- **원 확인 필요** — 원의 "노미네이트" 관념이 수동 지정일 수 있다.
  구체 선택지는 `open-decisions.md` Q2.

### D5. 1년차 공백 — 노미네이트 보드를 사이트의 얼굴로 (리드 지정 과제 ⑤)

charter §1의 가설("노미네이트 공개가 답일 수 있다")을 기능으로 확정한다:

- **홈 상단 = "2026 올해의 앨범 — 현재 노미네이트" 현황판.** 버킷별 보드
  요약 + 최신 평론. 리스트가 12월의 발표물이 아니라 **연중 진행형 지면**이
  된다.
- 12월(원이 정하는 시점)에 확정 전환: 보드 → "2026 올해의 앨범" 확정
  리스트 (원의 서문 1편 첨부 — 연말에 원이 쓰는 유일한 추가물). 이듬해
  보드는 빈 상태로 리셋 → `SS-6`
- 보드가 비어 있는 극초기(평론 0~5편)의 얼굴은 최신 평론 자체다.
  홈은 이 구간에서도 성립해야 한다 (Jonnathan 전달).
- 월말정산(CF-4)이 보조 리듬을 만든다 — 호두아카이브 월말정산이 국내
  실존 형식 (references-kr §3). **단 발행 강제 없음**: 그 달 평론이 0이면
  월말정산도 없다 (charter §3 빈도 무목표와 정합).

### D6. 정보구조 — 세 연결의 구현 (리드 지정 과제 ③)

charter가 요구하는 세 연결을 지면 구조로 확정한다:

```
                      홈 (노미네이트 현황판 + 최신 평론)
                       │
   ┌───────────────────┼───────────────────┐
   ▼                   ▼                   ▼
 리스트 지면          평론 페이지          음악 이야기
 · 10선(확정)     ◄── 점수·버킷·태그 ───► · 본문(장르사·계보·유행)
 · 장르 보드(진행) 항목│  본문             참조│ · 참조 앨범 목록
 · 월말정산       →평론│ "등장하는 이야기"─┘   · 세부 장르 태그
   전 항목 링크 100%   │ "이 장르의 보드"      (평론 있으면 링크,
                       ▼                       없으면 텍스트)
                  아카이브 (연도·장르·아티스트) ─ 아티스트 페이지
                  + 소개/기준 지면 (선별 규칙 명문화)
```

1. **리스트 → 평론** (charter §1): 모든 리스트 항목이 평론으로 클릭 1회
   연결. 빌드 검사로 강제 → `SS-8`
2. **평론 ↔ 음악 이야기** (charter §4 이해의 사다리): 음악 이야기의 앨범
   참조 목록에서 양방향 링크 자동 생성. 평론 페이지에 "이 앨범이 등장하는
   이야기" 자동 표시. 폴백 사슬(v1.1): **직접 참조 > 세부 태그 일치 >
   버킷 일치 > 미표시** → `SS-9` `SS-10`
3. **노미네이트 → 평론** (charter §1 함의 ②): 보드는 도출물이므로 정의상
   전 항목에 평론이 있다. 역방향도 잇는다 — 노미네이트된 앨범의 평론
   페이지에 "현재 ○○ 노미네이트" 배지 → `SS-4`

### D7. 발행 워크플로우 — 원의 접점은 "문서 + 4필드"가 상한 (리드 지정 과제 ④)

원이 평론 1편 발행에 하는 일의 전부:

| 원이 하는 것 | 성격 |
|---|---|
| 1. 글을 쓴다 | 집필 |
| 2. 앨범명·아티스트를 적는다 | 집필의 일부 |
| 3. 장르 버킷 1개를 고른다 (확정 목록 + "그 외") | 편집 판단 |
| 4. 점수를 매긴다 (0.0~10.0, 1자리) | 편집 판단 |
| 5. "안 들으면 손해인가" 체크 1문항 | 편집 판단 (USP-C) |
| (선택) 세부 장르 태그 | 옵션 — 안 달아도 전 기능 성립 (D1) |

원이 **하지 않는 것**: 발매일·레이블·커버 아트 확보(시스템: MB 조회 +
User 폴백 — B6), 노미네이트 지정(D4 자동), 리스트 갱신(자동), 링크
연결(자동), 공유 카드 제작(자동 — D8), 마크다운·git·배포(User 소유).

- **전달 방식(초기):** 원은 쓰던 도구(문서·메신저 무엇이든)로 글+필드를
  User에게 전달하고, User가 발행한다. 도구 학습 비용 0. 발행 빈도가 낮아
  (월 1~2편 규모) User 병목이 아니다.
- **전달 방식(추후):** 원 전용 입력 UI(git 기반 CMS 등)는 실측된 병목이
  생길 때 도입한다 — John의 A3 권고("파일 기반 시작, 병목 시 CMS
  마이그레이션")와 동일 구조. **도구 선택은 James(A3) 소유이며, 제약은
  하나다: 원의 접점이 위 표를 초과하면 안 된다.**
- 음악 이야기 발행: 글 + 참조 앨범 목록(글에 이미 등장하는 이름들) +
  세부 태그(옵션). 아티스트 소개 발행: 글 + 아티스트명. 둘 다 같은 파이프라인.

### D8. 채널 분리 — 이 사이트는 글 전용, SNS는 유통로 (v1.1 신규, 원 확정)

원 확정: *"숏폼 같은 것들은 인스타나 유튜브로 하고, 글 위주는 지금 하는
프로젝트로."*

1. **사이트에 영상·숏폼 기능을 넣지 않는다** (Non-goals 반영). 텍스트
   매거진이라는 형식 자체가 지형상 빈자리다 (references-kr §4 추론 2 —
   레퍼런스 셋 다 텍스트가 아니다).
2. **원의 SNS가 유입 축 ②(커뮤니티 유통)의 실체다.** Caleb이 유입 축을
   검색 → 리스트·결산 유통으로 전환하라 했고(usp-recommendations-v2 §1.3b),
   원 스스로 SNS 채널 병행을 상정했다. 사이트 쪽 접점은 하나다:
   **공유될 때 제대로 보이는 것** → `CF-11` 공유 카드. 링크를 붙여넣는
   것만으로 카드가 완성돼야 한다 (원의 추가 노동 0).
3. **사이트 → SNS 자동 포스팅은 만들지 않는다** (1차). SNS 운영은 원의
   채널 영역이고, 자동화는 병목 실측 후 판단.

### D9. 레퍼런스 세 방식의 텍스트 통합 — 성립한다, 단 "소식 정리"는 코너로 만들지 않는다 (v1.1 신규, 기획 판단)

원의 추가 답변으로 레퍼런스 셋이 **각자 다른 방식**으로 문턱을 낮춘다는
것이 드러났다. 원은 셋을 텍스트 하나로 합치려 한다. 판단:

| 레퍼런스의 방식 | 사이트의 자리 | 판단 |
|---|---|---|
| 통세우 — 힙합 앨범 해체·리액션 | **평론** (코너 1) | ✅ 그대로 흡수. "왜 이 앨범이 대단한가"의 텍스트판 |
| 우키팝 — 장르의 역사·유행 장르 소개 | **음악 이야기** (코너 2) | ✅ 그대로 흡수 — **이것이 §7.5 계보의 실체다** (아래) |
| 호두아카이브 — 소식을 깔끔하게 정리 | **코너로 만들지 않는다** | ❌ 아래 근거 |

**"소식 정리"를 코너에서 제외하는 근거 (기획 판단 — 원 이견 가능,
open-decisions 참고 목록에 명시):**
1. 소식은 유통기한이 짧다 — 축적 구조(리스트·아카이브)에 기여하지 않는
   유일한 형식이다. 이 사이트의 모든 지면은 연말 리스트를 향해 쌓인다.
2. 소식은 주기 압박을 만든다 — "이번 주 소식"은 매주를 요구하고, 이는
   "듣는 대로 씀"(charter §3) 및 1인 집필 제약(§6)과 정면 충돌한다.
3. 수요는 이미 흡수처가 있다 — "그 달을 정리"하는 수요는 월말정산(CF-4)이,
   속보성·가벼운 소식은 원이 분리한 SNS 채널(D8)이 맡는 것이 원의 채널
   구분과 정합한다.

**§7.5 계보의 실체 확정.** 원의 "선도한 앨범·따라가는 앨범 나열"(charter
§7.5)과 이번 "장르의 역사와 유행하는 장르 소개"는 같은 것을 가리킨다 —
음악 이야기의 주 형식은 **"이 장르(세부 태그)가 어디서 와서, 무엇이
유행이고, 어떤 앨범들이 그 흐름인가"**를 쓰는 글이다. 세부 태그(D1-②)가
그 앵커이고, 참조 앨범 목록(SS-9)이 그 나열이다. 데이터 층은 이것으로
확정이며, **시각 층만 Jonnathan 시안 → 원 선택으로 남는다.**

## 4. 에픽과 릴리스 순서

의존 관계가 순서를 강제한다: 리스트는 평론의 도출물이고, 사다리는 이야기
콘텐츠가 있어야 작동한다.

| 에픽 | 내용 (CF) | 순서 근거 |
|---|---|---|
| **E1. 평론 + 발행 파이프라인** | CF-1 · CF-9 · CF-10 · CF-11 | 모든 것의 원자재. 공유 카드는 페이지 단위 인프라이므로 여기 포함 (첫 평론부터 유통 가능해야 — D8) |
| **E2. 리스트 엔진** | CF-2 · CF-3 · CF-4 + 홈(CF-7 일부) | USP-A의 몸체이자 1년차의 얼굴 (D5). 평론 1편만 있어도 보드가 성립 |
| **E3. 탐색** | CF-7 아카이브 · CF-6 아티스트 | 글이 몇 편 쌓이면 즉시 필요. 구현 저렴 (빌드 인덱스) |
| **E4. 사다리** | CF-5 | 음악 이야기 1편이 나올 때 작동하면 된다. 데이터 층(참조·태그 필드)은 E1에서 확정 |
| **E5. 정체성 지면** | CF-8 소개/기준 | 콘텐츠 작성(원+리드 협의) 위주, 개발 최소. 공개 시점엔 있어야 함 |

**릴리스 판단:** E1+E2가 최소 공개 단위다 — "평론 몇 편 + 진행형 보드"가
첫 얼굴이며, E5는 공개 시점에 동반한다. E3·E4는 공개 후 순차. 단 **참조
필드·버킷·세부 태그 등 데이터 스키마는 E1에서 전부 확정**한다(나중에 소급
태깅하는 노동을 원에게 지우지 않기 위해 — 원칙 0-1).

## 5. 데이터 모델 요구사항 (James 전달)

W2 아키텍처가 충족해야 할 기획 측 제약. ERD는 James 소유.

1. **앨범**: 제목 · 아티스트(복수 가능) · 발매일(연도 필수) · **장르 버킷
   1개**(연도별 설정 목록 + "그 외") · **세부 장르 태그 0~n개**(등록부
   정규화 — D1) · 커버 · 스트리밍 링크(옵션) · 외부 ID(MB, 옵션)
2. **평론**: 앨범 참조 · 점수(0.0~10.0, 소수 1자리) · 발행일 · 본문 ·
   편집 체크 기록
3. **음악 이야기**: 본문 · 앨범 참조 목록 (역할 태그 옵션: 선도/추종 —
   계보 축. 시안 확정 전까지 옵션) · 세부 장르 태그(옵션)
4. **아티스트**: 이름 · 소개글(옵션). 페이지는 참조 집계로 자동 생성
5. **장르 버킷 목록**: 연도별 설정값 (코드 아닌 데이터). **세부 태그
   등록부**: 표기 정규화 사전 (User 관리)
6. **리스트**: 저장하지 않는다 — 빌드 타임 도출. 예외: **연간 확정
   스냅샷**(확정 시점의 순위·점수 동결 + 서문). 확정 후 점수 수정은
   아카이브에만 반영, 스냅샷 불변
7. **연도 귀속 규칙**: 연간 리스트 후보 = 발매 연도 기준. 확정 후 발행된
   지난해 앨범 평론은 리스트에 소급 반영하지 않는다 (리스트 = 발표 시점의
   선언). 구반 평론(저평가 앨범 등)은 리스트 밖, 아카이브에만
8. **공유 메타**: 전 공개 페이지가 유형별 카드 템플릿의 OG 메타를 보유 (CF-11)
9. **이식 가능성**: 전 콘텐츠가 도구 중립 형식으로 저장 (charter §5 —
   "나중에 열 수 있게"의 유일한 요구)
