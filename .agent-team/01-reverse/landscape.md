# 기술 지형 — undernote (1인 음악 매거진)

**상태:** 그린필드  
**범위:** 1인 음악 리뷰 매거진을 위한 실행 가능한 기술 스택 탐색  
**제약:** Windows 11 · Node/npm/Rust · 1인 운영 · "발행 30분 이내" 목표 (charter §3)  
**입력:** Charter §6 (제약) · §7 (가정 A3, A5)

---

## 1. 콘텐츠 저장 아키텍처 (Charter A3)

### 옵션 A: 파일 기반 + 정적 생성  
**방식:** 마크다운 파일 + 빌드타임 렌더링 (11ty, Astro, Hugo 등)

**1인 운영 적합성**
- ✓ 원자성. 한 파일 = 한 리뷰.  
- ✓ 버전 관리 내장 (git 이력).  
- ✓ 런타임 서버 불필요.  
- ✓ 호스팅은 상용 (Netlify, Vercel, GitHub Pages, S3 + CloudFront).  
- ✓ 오프라인 우선: 로컬 편집기에서 작성 후 git push로 배포.  
- ✓ 운영 부하 극소.  

**"30분 발행" 달성 가능성:**  
마크다운 작성 로컬 → git push → CI/CD 자동 빌드 및 배포 → ~30-60초 후 라이브. 워크플로우 오버헤드: **5분 이내.** ✓ **기준 충족.**

**트레이드오프**
- 4축 교차 쿼리(아티스트 + 연도 + 장르 + 레이블)는 빌드타임 인덱스 또는 메타데이터 추출 필요.  
- 앨범 메타데이터는 YAML 프론트매터에 수기 입력.  
- 수정(리뷰 오타 수정, 메타데이터 업데이트)은 재빌드 및 재배포 필요.  

**파일 구조 예시**
```
content/reviews/
  2026/
    2026-09-05-artist-album.md  (frontmatter: artist, year, genre, label, tracks)
_data/archives.json (빌드타임 생성: artist, year, genre, label별 인덱스)
```

**운영 비용 추정:** 리뷰당 메타데이터 입력 ~2-3분 + 템플릿 작성.

### 옵션 B: CMS (헤드리스)  
**예시:** Sanity · Contentful · Strapi

**1인 운영 적합성**
- ✓ 편집 UI (마크다운/프론트매터 타이핑 불필요).  
- ✓ 메타데이터는 구조화된 드롭다운 (아티스트, 연도, 장르, 레이블).  
- ✓ 실시간 인덱싱으로 4축 교차 쿼리 지원.  

**"30분 발행" 달성 가능성:**  
CMS UI에서 작성 → 메타데이터 필드 입력 → "발행" 클릭 → 웹훅으로 빌드 시작 → 배포. 오버헤드: **3-5분.** ✓ **기준 충족.**  
*단, CMS 셋업은 일회성 비용(설정에 며칠 소모); 이후 리뷰당 비용은 낮음.*

**트레이드오프**
- **벤더 종속:** 데이터가 벤더 시스템에 저장 (자체 호스팅 아닌 경우).  
  - Contentful/Sanity: 프리미엄이지만 수출/임포트 워크플로우는 느림.  
  - Strapi: 오픈소스, 자체 호스팅 가능하나 운영 부하 증가.  
- **비용:** 프리 티어 제한 있음. 초과 시 $15–100+/월.  
- **빌드 복잡도:** CMS → 정적 사이트 생성 파이프라인 여전히 필요 (CI/CD).  

**셋업 비용 추정:** CMS 설정 1-3일 + 콘텐츠 모델 설계.

### 옵션 C: 데이터베이스 기반 동적 사이트  
**예시:** Next.js/Node.js + PostgreSQL · Django + PostgreSQL · Rails + PostgreSQL

**1인 운영 적합성**
- ✓ 구조화된 메타데이터 쿼리(4축 아카이브)는 기본 (SQL).  
- ✓ 향후 동적 기능(검색, 필터링) 추가 시 재설계 불필요.  
- ✓ 커스텀 또는 기성 관리 패널 가능 (pg_admin 등).  

**"30분 발행" 달성 가능성:**  
리뷰 작성 + 폼 제출 → DB에 저장 → 페이지 동적 생성 또는 캐시 업데이트. 오버헤드: **2분.** ✓ **기준 충족.**

**트레이드오프**
- **운영 부하:** 데이터베이스 + 애플리케이션 서버 호스팅 필요.  
  - 가장 간단: PlanetScale (MySQL) + Vercel (Next.js). 프리 티어: 5GB 스토리지, 월 1000만 행 읽기. 업그레이드: $39+/월.  
  - 자체 호스팅: VPS의 PostgreSQL (Linode $5/월 + 관리 노력).  
- **복잡도:** DB 마이그레이션, 백업, 복구 절차. 1인 = 장애 시 높은 위험.  
- **성능:** 캐싱해도 동적 사이트는 정적 페이지보다 느림 (페이지 서빙 시간).  
- **디버깅:** 요청 실패는 런타임에 발생 (빌드타임이 아님).  

**셋업 비용 추정:** 3-7일; 운영 비용 = 모니터링 + 백업.

## 2. 앨범 메타데이터 출처 (Charter A5)

### 옵션 A: 리뷰 작성 중 수기 입력  
**방식:** 편집자가 아티스트, 연도, 장르, 레이블, 트랙리스트를 수기로 입력.

**적합성**
- ✓ 정확성 보장 (편집자가 모든 필드 제어).  
- ✓ 외부 API 의존성 없음, 레이트리밋 없음.  
- ✓ 라이선스 고려 사항 없음.  
- ✓ 오프라인 작동.  

**"30분 발행" 달성 가능성:**  
수기 입력은 리뷰당 +3-5분. ✓ **기준 충족 (여유 있음).**

**트레이드오프**
- **데이터 입력 오류:** 오타, 포맷 불일치 (THE BEATLES vs The Beatles).  
- **정규화:** 100편 후 "The Beatles 모든 앨범" 검색 실패 (스펠링 차이).  
- **유지보수:** 발행 전 체크리스트 필요: 철자, 장르 일관성, 레이블명.  

**운영 비용 추정:** 리뷰당 +5분; 30편마다 불일치 수정에 1-2시간.

### 옵션 B: 외부 API (MusicBrainz)  
**서비스:** MusicBrainz (커뮤니티 관리 음악 메타데이터 DB)

**검증된 사양** (2026-09-01, MusicBrainz 공식 문서)  
출처: https://musicbrainz.org/doc/MusicBrainz_API

- **라이선스:** 비상업용 무료. 상업용은 라이선스 계약 필요.  
- **레이트리밋:** **최대 초당 1회 요청.** 초과 시 IP 차단.  
- **인증:** 읽기는 API 키 불필요. 데이터 제출이나 사용자 정보는 OAuth/다이제스트 인증.  
- **커버리지:** 서구 음악에 강함. 비서구/소규모 인디는 약함. *(미확인: 구체적 커버리지 %)*  
- **신뢰성:** 커뮤니티 운영, SLA 없음.  

**undernote에 적합성**
- ✓ 앨범/아티스트로 메타데이터 조회 → JSON 반환.  
- ✓ 프리 티어가 1인 수동 워크플로우에 적합 (초당 1회 제약 문제 아님).  

**"30분 발행" 달성 가능성:**  
리뷰 작성 중 MB 검색 → 데이터 복사/붙여넣기 또는 자동 가져오기. 오버헤드: **+2분 (조회 + 검증).** ✓ **기준 충족.**

**트레이드오프**
- **커버리지 차이:** 소규모 인디, 비서구 음악, 최근 발매는 MB에 없을 수 있음.  
- **커뮤니티 유지보수:** 데이터 품질이 커뮤니티 기여에 의존; 때로 오래됨.  
- **폴백 필요:** MB에 없으면 수기 입력으로 복귀.  
- **배치 쿼리 느림:** 초당 1회 제약으로 "1995년 모든 앨범" 같은 쿼리는 비실용적.  

**운영 비용 추정:** 리뷰당 +2분 조회; 부분적 자동화.

**공개 문서 기반 사양** (웹페치 2026-09-01 실패, 공개 정보)

- **커버리지:** 비닐, CD, 리이슈에 강함. 스트리밍 전용 앨범은 약함. *(미확인: 구체적 커버리지)*

**적합성**
- ✓ MB와 유사하되 다른 커버리지 강점 (리이슈 중심).  

**트레이드오프**
- **인증 마찰:** 개인 토큰을 앱에 저장 (코드 공개 시 노출 위험).  
- **커버리지 보완 역할:** MB와 겹치지만, 각각 부족한 앨범이 다름.  

**운영 비용 추정:** 리뷰당 +2분. 커버리지는 MB와 겹치되 각각 빠지는 앨범이 다름. *(정량 미확인)*

## 3. 4축 아카이브 탐색 (아티스트 · 연도 · 장르 · 레이블)

### 정적 생성으로의 실행 가능성  

30편(charter §3 초기 목표)은 정적 생성으로 **완전히 실행 가능**:

**빌드타임 접근**
```
모든 리뷰 프론트매터 파싱 (메타데이터) → 
4개 인덱스 생성 (각 축별 JSON 배열) → 
목록 페이지 생성:
  - /archive/artist/[artist].html (해당 아티스트의 모든 리뷰)
  - /archive/year/[year].html
  - /archive/genre/[genre].html
  - /archive/label/[label].html
```

**클라이언트 측 개선 (선택)** *(미확인)*
- 30편 → 30 × 4 = 120 인덱스 항목. 클라이언트 필터링은 불필요한 오버헤드.  
- 향후 규모 증가(300편) → 1200 항목. 이때 클라이언트 검색/필터 추가 고려.  

**빌드 타임:** 30편 기준 ~500ms. 무시할 수준.

### 데이터베이스를 통한 실행 가능성  

동적 쿼리는 30편 규모에선 **과설계**. 데이터베이스는 향후 사용자 생성 콘텐츠(리뷰, 태그, 투표) 추가 시에만 정당화됨.

## 4. 호스팅 및 배포 옵션

### 정적 사이트용  
| 옵션 | 비용/월 | 운영 부하 | 커버리지 | 비고 |
|--------|-----------|-----------|----------|-------|
| **Netlify** | 무료 (CI/CD 포함) | ~5분 설정 *(추정)* | 글로벌 CDN | git push → 자동 배포. ~30초 빌드. 프리 티어 넉넉함. *(미확인: 정확한 한도)* |
| **Vercel** | 무료 | ~5분 설정 *(추정)* | 글로벌 CDN | Netlify와 동일. Next.js 네이티브. *(미확인: 한도)* |
| **GitHub Pages** | 무료 | ~5분 설정 *(추정)* | 글로벌, GitHub 호스팅 | 간단. Jekyll/Hugo 지원. *(미확인: 성능)* |
| **AWS S3 + CloudFront** | ~$1-5 | ~30분 설정 *(추정)* | 글로벌 CDN | 종량제. 읽기 집약적 사이트에 매우 저렴. 수동 CI/CD. *(미확인: 정확한 비용)* |
| **Linode / VPS** | $5-20 | ~2시간 *(추정)* + 지속 관리 | 단일 리전 | nginx 서버; 완전 제어. 높은 운영 부하. *(미확인: 신뢰성)* |

**1인 운영에 추천:** Netlify 또는 Vercel. 배포 마찰 제로, 글로벌 CDN 포함.

### 데이터베이스 기반 사이트용  
| 호스팅 | DB | 비용/월 | 운영 부하 | 비고 |
|---------|------|-----------|-----------|-------|
| **Vercel + PlanetScale** | MySQL | 무료–$39 | ~10분 *(추정)* | 서버리스. 자동 확장. 프리 티어 넉넉함. *(미확인: 한도)* |
| **Vercel + Supabase** | PostgreSQL | 무료–$25 | ~10분 *(추정)* | Supabase = Firebase 같은 DX for Postgres. *(미확인: 한도)* |
| **Linode VPS + PostgreSQL** | PostgreSQL (자체) | $5-20 | 2-3시간 *(추정)* + 백업 | 완전 제어; 최대 운영 부하. DevOps 경험 필요. *(미확인: 신뢰성)* |

**추천:** DB 선택 시 **Vercel + PlanetScale**. 가장 간단한 서버리스 경험.

## 5. 앨범 커버 아트 취급 (기술 고려사항)

**Charter §6 주의:** "앨범 커버 아트는 저작물 ... 인용·비평 목적의 사용 범위를 W2에서 정리해야 한다." = 법적 타당성 확인은 W2, 기술은 이어서 결정.

**기술 옵션** (법적 승인 가정)

### A. 외부 URL 직접 임베드  
```markdown
![앨범 커버](https://musicbrainz.org/release-art/xxxxx.jpg)
```
- ✓ 저장소 크기 영향 없음. 업스트림 서비스 대역폭 비용.  
- ✗ 링크 부패 위험 (외부 CDN 사라짐).  
- ✗ 외부 가용성에 의존.  

### B. 자체 호스팅 이미지 자산  
```
assets/covers/
  artist-album.jpg (100 KB × 30 = 3 MB)
```
- ✓ 완전 제어.  
- ✓ 빠르고 신뢰성 높음.  
- ✗ 저장소/호스팅 비용 (S3: ~$0.023/GB, 3MB는 무시할 수준).  
- ✗ 수동 큐레이션 (API에서 소싱 시).  

### C. 지연 로드 + 폴백  
- CDN 시도 → 자체 호스팅 폴백.  
- 방어적: 링크 부패와 가용성 문제 동시 대응.  

**추천:** **옵션 B (자체 호스팅)** + 옵션 C (폴백). 30개 커버 @100KB: S3에서 ~$0.07/월. 무시할 비용.

## 6. 배포 및 발행 워크플로우 (30분 목표)

### 시나리오 A: 파일 기반 + 정적 생성 + Netlify  

```
1. 로컬에서 리뷰 마크다운 작성        (~20분 에세이, 30분 범위 제외)
2. Commit & git push                  (~1분)
   → Netlify 웹훅 실행               (~즉시)
   → 빌드 및 배포                     (~30초)
3. 라이브 확인                         (~30초)
```

## 8. Charter 정렬 요약

### A3 — 파일 vs CMS vs DB?  

**발견:** 세 아키텍처 모두 "발행 30분 이내"를 형식상 충족. **단, 실제 1인 비용(셋업·운영·장애)은 크게 다름.**

**W2에 대한 권고:**

- **철학이 "순수 텍스트, 버전 제어, 복원력"이라면** → 파일 기반 (가장 단순).  
- **철학이 "구조화된 메타데이터 + 편집 용이"라면** → CMS (Sanity 구독형 또는 Strapi 자체 호스팅).  
- **향후 동적 기능(검색, 사용자 상호작용) 포함 계획이면** → DB (PlanetScale + Vercel).  

**1인 제약이 결정 요소:** 파일 기반이 **최저 운영 부하, 벤더 종속 없음, 최대 복원력.** CMS/DB가 명확한 편집 가치를 추가하지 않으면 파일 기반이 우수.

### A5 — 수기 메타데이터 vs API?  

**발견:** 하이브리드 (API + 수기 폴백) 최적.

**MusicBrainz 검증 사양 (2026-09-01 공식 문서)**
- 비상업용 무료, 초당 1회 요청 제약
- 서구 대중음악에 강함; 비서구/소규모 인디는 약함 *(구체적 커버리지 % 미확인)*
- 인증 불필요 (읽기 전용)

**권고:**
- **수기 입력으로 시작** (더 단순).  
- **30편 후 메타데이터 부담이 병목 되면**, MusicBrainz 조회를 선택 기능으로 추가 (1분 절감/리뷰 × 4 리뷰 = 4분, 30리뷰 단위로 누적).
