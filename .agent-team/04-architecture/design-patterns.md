### P1. Derive, don't store — 파생물 비저장 + 템플릿의 판단 금지

- **무엇:** 리스트·인덱스·역링크·배지는 매 빌드 전량 재계산. 페이지 템플릿은
  derive 출력(`api-contracts.md` §4)의 순수 소비자 — 정렬·필터·귀속 판단이
  템플릿에 들어가면 반려.
- **왜:** USP-A의 불변식("리스트 = 평론의 인덱스")은 저장된 리스트가 없어야
  구조적으로 보장된다 (D3·D4). 판단이 한 곳(derive)에 있어야 결정성
  규칙(R-1~R-10)이 테스트 가능하다.
- **피한 것:** 리스트 파일 수동 관리(원의 노동 + 어긋남 가능), 증분 캐시
  (수백 파일 규모에서 순수 비용).

### P2. Schema-first content — 계약이 코드보다 먼저

- **무엇:** 프론트매터 JSON Schema(`api-contracts.md` §3)가 SSOT.
  `content.config.ts`(Zod)는 그 번역이며, 의미 변경은 문서부터.
  `additionalProperties: false`로 미지 필드 즉시 검출.
- **왜:** SS-1(필수 필드 = 빌드 실패)이 제품 약속의 1차 관문. 오타 필드가
  조용히 무시되면 옵션 기능(태그·역링크)이 침묵 실패한다.
- **피한 것:** "일단 파싱되면 통과" 방식의 관용적 읽기.

### P3. Snapshot freeze — 불변의 예외는 한 곳에

- **무엇:** 확정 연간 리스트만 파일로 동결(표시 문자열까지 비정규화 저장),
  이후 어떤 입력 변화에도 불변 (R-2). 그 외 전 지면은 살아 있는 도출물
  (월말정산 포함 — R-5).
- **왜:** "리스트 = 발표 시점의 선언" (§5 요구 6·7). 불변 지면이 여럿이면
  수정 전파 규칙이 조합 폭발한다 — 예외를 하나로 몬다.
- **피한 것:** 월말정산 스냅샷화, DB식 이력 테이블.

### P4. Registry normalization — 자유 어휘의 등록부 정규화

- **무엇:** 세부 태그는 canonical slug + aliases 등록부(`config/tags.yaml`)로
  정규화. 미등록 표기는 경고 + 등록 제안 (E-201).
- **왜:** "인디 록" vs "indie-rock"이 30편에 걸쳐 갈라지면 태그 축·역링크
  폴백이 조용히 반토막 난다 (John의 미확인 항목에 대한 구조적 답).
- **피한 것:** 자유 태그 방치, 반대로 태그 승인제(원의 노동 — D7 위반).

### P5. Fallback chain — 단계적 저하, 빈 껍데기 금지

- **무엇:** 역링크(직접 > 태그 > 버킷 > 미표시 — 섞지 않고 최초 비지 않는
  단계만), 커버(사본 > 플레이스홀더), OG 이미지(커버 카드 > 텍스트 기본형),
  듣기 링크(수기 > 자동 검색형 > 영역 미표시), 메타데이터(MB > 수기).
- **왜:** 옵션 데이터의 부재가 발행을 막으면 안 되고(D1·D7), 부재가 깨진
  UI로 보여도 안 된다 (R-4: 채우지도 사과하지도 않는다).
- **피한 것:** 필수화(원 부담 증가), 빈 영역 렌더.

### P6. Tool-neutral content — 이식성은 형식으로 지킨다

- **무엇:** `content/`는 순수 Markdown + YAML. SSG 전용 문법·컴포넌트 임베드
  금지. 파생 가능한 값(링크·집계)은 저장하지 않는다.
- **왜:** charter §5가 남긴 유일한 미래 대비 — "구조화 저장으로 나중에 옮길
  수 있게". 확장 대비 설계(계정·DB 스키마)는 금지지만 이식 가능성은 의무다.
- **피한 것:** MDX 본문, 프론트매터에 렌더 힌트 저장.

### P7. Fail-fast build, 3-tier severity — 실패·경고·알림의 분리

- **무엇:** E-1xx(배포 중단)·E-2xx(경고)·E-3xx(원 전달 알림)의 3등급
  (`exceptions.md`). 실패는 전부 모아 한 번에 보고. 실패해도 기존 사이트는
  마지막 성공 상태로 서빙된다.
- **왜:** "부분 발행 없음"(SS-1)과 "옵션 부재가 발행을 막지 않음"(D1)을
  동시에 만족하려면 등급이 계약이어야 한다. 등급이 코드 곳곳의 재량이면
  같은 문제가 어떤 날은 실패, 어떤 날은 통과가 된다.
- **피한 것:** 경고의 실패 승격 남용(발행 마비), 전부 경고화(약속 붕괴).

### P8. Kill-switch config — 정책 변경을 설정 1개로

- **무엇:** 법적·정책적으로 되돌릴 수 있어야 하는 판단(커버의 OG 사용 등)은
  `config/site.yaml` 플래그로 노출 (ADR-0008).
- **왜:** 커버 아트 실무 판단에는 "미확인 — 법률 검토 필요" 항목이 남는다.
  판단이 뒤집혔을 때 코드 수정 없이 다음 빌드로 전 지면 반영되는 것이
  아키텍처의 책임이다.
- **피한 것:** 정책의 하드코딩 산재.

### P9. Human-in-the-loop, no auto-resilience — 재시도 기계 대신 사람

- **무엇:** 외부 호출(MB·CAA)은 편집 시점 CLI에만 있고, 실패 처리는 1회
  재시도 + 수기 폴백 프롬프트다. 서킷브레이커·큐·백오프 루프 없음.
- **왜:** 호출 지점에 항상 사람(User)이 앉아 있다. 자동 복원은 무인
  시스템의 도구 — 여기선 복잡성만 산다 (`exceptions.md` 3부). 멱등성 문제도
  같은 이유로 소멸: 쓰기는 로컬 파일 생성이고 재실행 = 덮어쓰기다.
- **피한 것:** 편집 도구의 데몬화, 발행 자동화 파이프라인(D8 — SNS 자동
  포스팅 비범위와 같은 원칙).

### P10. Fixed total order — 우연이 낄 자리를 없앤다

- **무엇:** 전 정렬은 3키 전순서(R-1), 점수 연산은 십분위 정수(ADR-0004),
  시간대 고정(R-10), 로케일 비교 금지. 동일 저장소 = 동일 사이트 (CI에서
  2회 빌드 해시 비교).
- **왜:** 순위가 곧 제품이다 (charter §1: 점수는 연말 순위를 위한 기록).
  빌드마다 순서가 흔들리는 리스트는 권위를 스스로 부순다.
- **피한 것:** 부동소수 직접 비교, 파일 시스템 순회 순서 의존, `new Date()`
  산재.
