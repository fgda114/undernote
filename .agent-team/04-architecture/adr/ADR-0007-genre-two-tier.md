# ADR-0007. 장르 = 연도별 버킷 설정 + 세부 태그 등록부 (2층 분리)

## 맥락

장르의 두 용도는 성질이 반대다: 리스트 버킷(굵고 적고 고정적, 연간 부담 결정) vs
설명 대상(세밀하고 자유롭고 많을수록 가치). 하나의 분류 체계로 묶으면 양쪽 다 죽는다.
또한 과거 연도의 리스트는 그해의 버킷 구성으로 고정되어야 한다 (D1: 연 단위 설정값).

## 결정

**세 가지 실체로 분리한다. 셋 다 코드가 아니라 데이터다:**

1. **버킷 = 연도별 설정** `config/genres.yaml` — 연도 키 아래 그해의 버킷 목록·라벨·발행 최소 편수. **과거 연도 블록은 수정하지 않는다**(관례 + 스냅샷 비정규화가 이중 방어). 원이 이듬해 구성을 바꾸면 새 연도 블록만 추가 — 코드 수정 0.
   - 앨범의 `bucket` 값 검증은 **발매 연도의 설정 블록** 기준 (E-102). `etc`("그 외")는 모든 연도에 암묵 존재.
2. **세부 태그 등록부** `config/tags.yaml` — canonical slug → 표시명 + 별칭 목록. 빌드가 별칭을 canonical로 정규화, 미등록 표기는 경고 + 등록 제안 (SS-1 v1.1, "인디 록" vs "indie-rock" 문제의 답). User 관리.
3. **설명 대상으로서의 장르 = 데이터가 아니라 콘텐츠** — "생소한 장르 설명"은 세부 태그를 앵커로 단 음악 이야기(D9)다. 장르 계층 트리·온톨로지를 만들지 않는다. 태그는 평평한 어휘집이며 어떤 리스트 로직도 태그에 의존하지 않는다(사다리 폴백 SS-10 ②와 태그 아카이브 축 SS-11만 소비).

## 대안

1. **단일 계층형 장르 트리** — 버킷 요구(적고 고정)와 설명 요구(세밀·자유)를 동시에 못 맞춘다. 유지 노동이 원에게 전가될 위험. 기각.
2. **버킷을 앨범이 아닌 평론에 귀속** — 보드는 앨범 단위 경쟁이므로 앨범 속성이 맞다(발매 연도와 같은 곳). 기각.
3. **태그 자유 입력(등록부 없음)** — 표기 흔들림으로 태그 축 아카이브·사다리 폴백이 조용히 파편화. John이 지목한 실제 리스크. 기각.

## 결과

- (+) Q1 미답이 차단이 아니게 된다 — 어떤 답이 와도 `genres.yaml`의 값만 바뀐다.
- (+) 과거 리스트의 불변성이 설정 이력 + 스냅샷으로 이중 보장.
- (−) 태그 등록부라는 관리물 1개 추가 — User 소유, 원 접점 불변(태그는 옵션).
