# ADR-0001. 콘텐츠 저장 = 파일 기반 + 정적 생성 (charter A3 확정)

| | |
|---|---|
| 상태 | **Accepted** (charter B5 · John A3 권고의 아키텍처 비준) |
| 작성 | James · 2026-09-01 |
| 입력 | `01-reverse/reverse-summary.md` A3 · charter §5·§6 · Joshua 원칙 0-3 |

## 맥락

- 집필 1인(원) + 개발 1인(User). 유저 참여 없음 — 계정·댓글·평점 전부 비범위이며 **확장 대비 설계 금지** (charter §5).
- 콘텐츠 규모: 연 ~15~25편 + 음악 이야기 + 아티스트 소개. 수년 누적해도 수백 파일.
- 유일한 미래 요구: **콘텐츠의 도구 중립 저장** (이식 가능성 — charter §5, Joshua §5.9).
- John의 전생명주기 비용 분석: 파일 기반이 셋업 최단(1–2일)·운영 최소·벤더 종속 없음.

## 결정

**모든 콘텐츠와 설정을 git 저장소 안의 플레인 텍스트 파일(Markdown + YAML/JSON)로 저장하고, 빌드 타임에 정적 HTML로 생성한다. 런타임 서버·DB·API 서버는 두지 않는다.**

- 백업·이력·롤백 = git. 별도 운영 체계 없음.
- 파생물(리스트·인덱스·역링크·OG 카드)은 전부 빌드 타임 계산 (ADR-0005).
- 배포 사이트에서 외부 API 호출 0 (MB 조회는 편집 시점만 — ADR-0006).

## 대안

1. **헤드리스 CMS + 정적** — 셋업 2–4일, 벤더 종속, 원이 CMS를 배울 이유가 없음(D7: 원은 문서로 전달, 발행은 User). 병목이 실측되면 그때 마이그레이션 — 콘텐츠가 파일이므로 재설계 불필요.
2. **DB + 동적 렌더링** — 백업·모니터링 운영 부담이 1인 개발에 상시 비용. 동적 기능(투표·검색·개인화)이 전무해 DB가 갚을 빚이 없다. charter §5가 명시적으로 금지한 "미리 DB" 케이스.

## 결과

- (+) 장애 모드가 "호스팅 CDN 다운" 하나로 줄어든다. 사이트 자체는 부술 상태가 없다.
- (+) 이식 가능성 요구가 공짜로 충족 — Markdown/YAML은 어떤 도구로도 옮겨진다.
- (−) 발행에 빌드+배포(수 분)가 낀다 — 발행 주체가 User이고 월 1~2편 규모라 병목 아님 (D7).
- (−) 미래에 유저 참여를 열려면 그 시점에 별도 설계 필요 — charter가 명시적으로 수용한 트레이드오프.
