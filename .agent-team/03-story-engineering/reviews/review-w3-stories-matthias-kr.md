## 3. Findings

### C-1. source_hash 신선도 게이트 발화 — **해소됨 (게이트 진행 중 수정 확인 — 실측 재검증 완료)**

> **해소 확인 (2026-09-02, 리뷰 중):** Matthew가 D3 규칙에 따라 source_hash를 재계산해 7개 파일(헌법 + 스토리 6편) 전부 `e6503e3e…709b67`로 갱신했고, 본 검증자가 §12 절차를 재실행해 **정확히 일치함을 실측 확인**했다. 게이트는 현재 통과 상태다. 아래 원 지적은 기록으로 보존하며, 잔여 리스크 1건만 non-critical로 강등한다 (N-0).
>
> **N-0 (잔여 — non-critical): §12 절차의 환경 의존.** 갱신된 `e6503e…`는 **CRLF 작업 트리** 기준 값이다. git blob(LF) 기준 동일 상류는 `8301726e…`로 다르다 — `core.autocrlf` 설정이 다른 체크아웃(예: Linux CI·재클론)에서 §12를 실행하면 상류가 안 변했어도 stale 오탐이 난다. 수정 권고: §12를 작업 트리 `cat`이 아니라 `git show HEAD:<path>` 연결 기반으로 교정 (eol-비의존·결정적). 현 개발 환경(이 머신 단일)에서는 실해 없음.

#### (기록) 원 지적 — 리뷰 시점 상태

- **위치:** 스토리 6편 전부의 frontmatter `source_hash` + `project-context-kr.md` §12.
- **실측 증거 (전부 이 환경에서 직접 실행):**
  - 선언값: `a1f222d8…3de266` (6편 + 헌법 동일)
  - §12 절차를 현 작업 트리에서 실행한 결과: `e6503e3e…709b67` — **불일치**
  - git blob(LF) 기준 재산출: 커밋 `69a4414` 시점 상류 = `a1f222d8…` (선언값과 **일치**) / 현 HEAD `819bb58` 상류 = `8301726e…0183da7`
- **원인 (증명됨):** 스토리는 `69a4414` 시점 상류로 컴파일됐는데, **같은 커밋 `819bb58`에서 ADR-0002가 개정**(Astro 5 → 7.x)되어 상류가 변했다. 즉 선언 해시는 스토리가 태어난 커밋에서 이미 낡았다. 추가로, 이 Windows 작업 트리는 CRLF 체크아웃이라 §12의 `cat | sha256sum` 절차는 **어떤 올바른 값도 재현할 수 없다** (LF blob 해시 ≠ CRLF 작업 트리 해시 — 환경 의존, 결정성 원칙 R-10과 같은 계열의 결함이다).
- **왜 critical인가:** §12 자기 규칙이 "불일치 = stale = **구현 착수 금지, 리드 보고**"다. Andrew가 W5.0 첫날 이 절차를 실행하면 6편 전부가 차단되거나, 무시하는 법을 배운다 — 어느 쪽이든 이 제품의 핵심 규율(신선도 게이트)이 첫날 죽는다. 참고: 리뷰 중 `project-context-kr.md`·`story-w5-0-setup-kr.md`에 미커밋 수정(Astro CONCERNS 해소 반영)이 진행 중임을 확인 — 이 수정에도 source_hash 갱신은 없다.
- **수정 방법:** ① 진행 중인 Astro 해소 수정을 커밋 ② §12 절차를 eol-비의존으로 교정 (`git show HEAD:<path>` 연결 또는 `git cat-file` 기반 — 작업 트리 `cat` 금지) ③ 그 절차로 재산출한 값을 6편 + 헌법에 일괄 갱신. 스토리 본문 재컴파일은 불요 — 스토리 내용은 개정 ADR(7.x)과 이미 정합한다(개정 자체가 W3 발견의 반영이므로). 수정 후 재검증은 명령 1회다.

### N-1. E-115 카드(PNG) 측 음성 테스트 메커니즘 미정의 — non-critical

- **위치:** `story-w5-2-list-engine-kr.md` AC7.
- **문제:** AC7의 검증 수단은 "렌더 산출 HTML 전수 검사"인데, satori가 구운 **PNG 카드 안의 점수 문자열은 HTML 스캔으로 잡을 수 없다.** "Given OG 메타·카드에 점수 문자열 / Then E-115 실패"의 카드 절반은 이 수단으로 반증 불가능하다.
- **실효 강제 수단은 이미 존재한다:** W5.1 testing의 "og 데이터 조립(점수 문자열 부재 검사)" 단위 테스트 — 점수가 og 모듈에 아예 전달되지 않는 데이터 계약. 
- **수정:** W5.2 AC7에 1줄 명시 — "카드 측 강제 = og 데이터 조립 입력에 score 부재(W5.1 단위 테스트), HTML 스캔은 메타 측 담당". 검사 지점을 특정하지 않으면 구현자가 "HTML 스캔 통과 = E-115 완료"로 오해할 수 있다.

### N-2. 홈 "최신 글" 섹션의 점수 비표시(D2) 자동 검사 부재 — non-critical

- **위치:** `story-w5-2-list-engine-kr.md` AC11~13 · testing requirements.
- **문제:** ui-spec §1.1은 홈 최신 글 목록을 "점수 비표시 (D2 탐색 지면)"로 규정하나, W5.2의 어느 AC·테스트도 이를 검사하지 않는다 (AC11은 보드만). 점수-프로퍼티-없는 ArticleCard는 **W5.3**에서 오는데 홈은 **W5.2**에서 만든다 — 이 시차 동안 홈 카드에 점수가 새어도 잡는 자동 검사가 없고, W5.5 수동 체크(design-handoff §5)까지 밀린다.
- **수정:** W5.2 testing에 1줄 — "홈 최신 글 카드 데이터에 score 필드 미전달 검사" (W5.3 ArchiveItem과 같은 데이터 계약 방식).

### N-3. 홈 "확정 직후 변형"(ui-spec §1.6)이 작업에만 있고 AC 부재 — non-critical

- **위치:** `story-w5-2-list-engine-kr.md` 작업 4 ("홈 3+1상태") vs AC9·10.
- **문제:** AC9·10은 finalize의 데이터 효과(스냅샷·active_year)만 검증한다. "확정 리스트 링크 카드 + 새해 빈 보드" 홈 렌더 상태는 작업에만 있어 통과 판정 기준이 없다 — 검증이 W5.5 수동으로만 가능해진다.
- **수정:** AC9에 Then 1절 추가 또는 통합 테스트에 "finalize 후 빌드 → 홈이 §1.6 변형으로 렌더" 명시.

### N-4. build-plan §3 "R-1~R-10 각 1케이스" 대비 R-9 누락 + E-302/303 무테스트 — non-critical

- **위치:** `story-w5-2-list-engine-kr.md` testing requirements (R-1~R-8·R-10만 열거) · Dev Notes (E-302·303).
- **문제:** R-9(slug·URL 불변)는 운영 규율이라 단위 테스트가 무의미할 수 있으나, 상류(build-plan §3)가 "각각 최소 1케이스"를 명시한 이상 **의도적 생략임을 스토리가 말해야** 한다 — 침묵 누락은 커버리지 회계를 흐린다. E-302(해 넘김 미확정)·E-303(보드 진입/탈락)은 Dev Notes에만 있고 AC·테스트 어디에도 없다 (AC8의 notices 구조 검사가 간접 커버할 뿐).
- **수정:** testing에 "R-9는 운영 수칙으로 검증 (git 이력 감사) — 단위 테스트 비대상" 1줄 + E-302/303 각 1 픽스처를 notices 검사에 포함.

### N-5. W5.5 조기 실행 경로(E3·E4 생략 공개)가 검증 불가능 상태 — non-critical

- **위치:** `story-w5-5-identity-launch-kr.md` frontmatter `depends_on: w5-2` + developer_context 마지막 항.
- **문제:** E3(아카이브)·E4(이야기) 없이 공개하는 경로에서 Masthead의 "아카이브"·"이야기" 링크는 **E-112(내부 링크 깨짐 = 빌드 실패)와 정면 충돌**한다. 스토리는 이를 "리드와 확인"으로 정직하게 표기했으나, 이 구성으로는 빌드가 성립하는지 자체가 미정의라 조기 공개 옵션은 현재 테스트 불가능하다. 기본 순차 경로(W5.2→3→4→5)에는 영향 없음.
- **수정:** 조기 공개 옵션 행사 전 결정 1건 기록 (내비 항목 조건부 제거 vs E3까지 대기) — 스토리 AC로 승격하거나 옵션 자체를 접거나.

## 4. 그 외 확인 사항 (문제 없음 — 기록만)

- **검증 가능성:** 전 AC가 Given/When/Then + 판정 수단(빌드 실패 코드·픽스처·해시·실측)을 갖는다. "잘 작동한다"류 모호어 0. 통과 판정 주체도 명확 (자동 게이트 / W5.5 AC7 Matthias 수동 전수).
- **상태 커버리지:** 평론 0편 홈(W5.2 AC12)·극초기(AC12, 임계값 설정화)·5편 미만 버킷(AC11)·폴백 사슬 4모드(W5.4 AC2~4 + 픽스처 ladder-direct/tag/bucket/none)·MB 미등재(W5.1 AC8)·커버 부재(AC11)·월 0편(W5.2 AC4)·소개 없는 아티스트(W5.3 AC6)·etc 버킷(W5.2 AC2) — ui-spec 상태 매트릭스가 AC로 실렸다.
- **테스트 전략의 실체:** 단위+픽스처+골든 파일+CI 해시 2회+W5.5 수동 인수. E2E 자동화를 만들지 않은 것은 이 규모(1인·정적 사이트·화면 8종)에서 옳은 절제다. 1인 개발자가 실제로 돌릴 수 있는 규모다.
- **원의 접점 상한(D7):** W5.1 스토리 자체가 D7 경로(글+4필드+체크 1문항)로 서술되고 AC14가 end-to-end로 검증한다. 어느 스토리도 원에게 추가 입력을 요구하지 않는다.
- **min_reviews_to_publish 정합:** W5.0 초기값 3 ↔ US-13 AC3 "2편 이하 미발행" ↔ W5.2 AC9 "≤min-1 → published:false" — 삼자 일치 확인.
