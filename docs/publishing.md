# 발행 — 새 글을 사이트에 올리는 법

이 문서는 두 사람을 위해 쓰였습니다. 각자 자기 몫만 읽으면 됩니다.

- **글 쓰는 사람** — [바로 아래 §1](#1-글-쓰는-사람용)
- **개발 담당** — [§2](#2-사용자개발-담당용)부터

구현물은 `tools/publish-desk/`에 있습니다 (비공개 저장소에 그대로 올릴 파일 트리). 이 문서
자체는 이 공개 저장소에 남습니다.

## 1. 글 쓰는 사람용

### 평론을 쓸 때

1. 새 글 쓰기 화면을 엽니다 (개발 담당이 알려준 주소로 들어가면 "새 글 쓰기 — 평론"이라는 버튼이
   보입니다).
2. 아티스트 이름, 앨범 이름, 발매일, 장르, 점수를 적습니다. 발매일을 정확히 모르면 연도만
   적어도 됩니다.
   - "(선택) 부제" 칸에 앨범명 옆에 함께 보일 짧은 부제를 적을 수 있습니다(예: "정규 3집",
     "The 3rd Studio Album"). 없으면 비워두면 됩니다 — 지면에 그 줄 자체가 안 나옵니다.
   - "(선택) 앨범 길이" 칸에 앨범 전체 재생 시간을 "분:초"로 적을 수 있습니다(예: "52:26").
     1시간이 넘으면 "92:15"처럼 분을 60 넘게 적으면 됩니다 — "1:32:15"처럼 시:분:초로 나누지
     마세요. 없으면 비워두면 됩니다.
   - "태그" 칸에 이 앨범을 설명하는 짧은 말을 쉼표로 구분해 적을 수 있습니다(예: "시티팝,
     드림팝"). 한글로 적어도 됩니다. 없으면 비워두면 됩니다.
3. "최종 확인했습니다" 체크를 합니다. **이 체크가 없으면 아무리 글이 완성돼 있어도 올라가지
   않습니다.**
4. 커버 사진이 있으면 그 칸에 파일을 끌어다 놓습니다. 없어도 됩니다 — 기본 이미지로 먼저
   나가고 나중에 넣어도 됩니다.
5. 본문을 씁니다. 마크다운을 몰라도 됩니다 — **문단을 나눌 때 그냥 Enter를 한 번 치면 됩니다.**
   맞춤법이나 띄어쓰기, 마침표는 고치지 않고 쓰신 그대로 나갑니다.
   - 특정 단어에 링크를 걸고 싶으면 `[이 곡](https://주소)` 처럼 대괄호 다음에 괄호로 주소를
     적으면 됩니다.
   - 문장을 `-`나 `#`, 숫자와 마침표(`1.`)로 시작하면 화면에서 목록이나 제목처럼 보일 수
     있습니다. 흔한 경우는 아니지만, 이상하게 나온 게 보이면 개발 담당에게 알려주세요.
6. 맨 아래 초록색 버튼을 누릅니다.

**"(선택) 부제"·"(선택) 앨범 길이"·"태그"는 새 앨범을 처음 등록할 때만 반영됩니다** — 이미
있는 앨범(다른 분이 먼저 다룬 앨범, 또는 개발 담당이 미리 만들어 둔 앨범)에 대한 평론을 낼 때
이 세 칸을 채워도 반영되지 않습니다(그 칸을 채웠다는 사실은 저장 후 댓글의 "참고" 항목에
남습니다). 커버 사진과 달리 이 셋은 나중에 "고치기"로도 바꿀 수 없습니다 — 정말 고쳐야 한다면
개발 담당에게 알려주세요.

### 이야기를 쓸 때

제목과 본문만 있으면 됩니다. 글에서 다룬 앨범이 있으면 "언급한 앨범들" 칸에 한 줄에 하나씩,
`앨범 이름 (아티스트 이름)` 형식으로 적어주세요. 이미 평론이 있는 앨범이면 자동으로 링크가
걸리고, 아직 없어도 나중에 그 앨범 평론이 올라오면 자동으로 링크가 생깁니다 — 다시 손댈 필요
없습니다.

"태그" 칸에 이 글을 설명하는 짧은 말을 쉼표로 구분해 적을 수 있습니다(예: "여름,
플레이리스트"). 한글로 적어도 됩니다. 없으면 비워두면 됩니다 — 평론과 달리 이야기의 태그는
나중에 "고치기"로 자유롭게 바꿀 수 있습니다.

### 저장한 다음

- **문제가 없으면** 보통 몇 분 안에(길면 10분 정도) 실제 사이트에 올라갑니다.
- **뭔가 잘못 적으면** 사이트에 올라가지 않고, 이 화면에 댓글로 무엇이 잘못됐는지 알려드립니다.
  한국어로, 어느 칸이 문제인지 구체적으로 나옵니다 (예: "점수는 소수점 첫째 자리까지만 —
  8.35가 아니라 8.3 또는 8.4로 적으세요"). **그 칸만 고쳐서 저장하면 자동으로 다시 시도합니다**
  — 처음부터 새로 쓸 필요 없습니다.
- 새 아티스트나 새 앨범을 처음 다룰 때, 이름이 한글이면 "영문 표기를 알려달라"는 댓글이 달릴
  수 있습니다. 로마자로 한 번만 적어주면 됩니다(예: phoebe-bridgers) — 다음부터 같은
  아티스트를 다시 다룰 때는 안 물어봅니다.

### 나중에 고치고 싶을 때

한 번 올라간 글도 그 화면을 다시 열어서 고치고 저장하면 됩니다 — 새로 쓸 필요 없습니다.

- **고칠 수 있는 것**: 본문(글), 점수, 커버 사진. 커버를 처음엔 비워뒀다가 나중에 사진을
  끌어다 놓아도 됩니다 — 있던 사진을 바꾸고 싶을 때도 새 사진을 끌어다 놓고 저장하면 됩니다.
- **고칠 수 없는 것**: 아티스트 이름, 앨범 이름, 발매일, 장르(이야기는 제목). 이 칸들은 그
  글의 인터넷 주소나 분류를 정하는 값이라, 한번 정해지면 이 화면에서는 바꿀 수 없습니다. 이
  칸 중 하나라도 처음과 다르게 저장하면 **아무것도 바뀌지 않고**, 무엇이 왜 안 되는지 댓글로
  알려드립니다 — 그 칸을 원래 값으로 되돌리고 나머지(본문·점수·커버)만 고쳐서 다시 저장하면
  됩니다. 정말 아티스트 이름 등을 바로잡아야 한다면 댓글에 적힌 대로 개발 담당에게 알려주세요.
- 점수를 고쳐도 이미 확정해서 발표한 연말 리스트(그해가 끝나고 순위를 확정한 지면)는 바뀌지
  않습니다. 리스트는 "그때 발표한 그대로" 남는 것이 이 매거진의 원칙입니다 — 당황하지 않으셔도
  됩니다, 의도된 동작입니다.

### 글을 내리고 싶을 때

개발 담당에게 요청하면 그 글을 사이트에서 내려줍니다. 내려간 글의 주소로 다시 들어오면 "글을
찾을 수 없다"는 안내 지면으로 이동합니다.

한 앨범을 다룬 글이 그 앨범을 소개하는 유일한 글이었다면, 그 앨범과 아티스트 소개 페이지도
함께 정리됩니다(다른 글이 여전히 그 앨범/아티스트를 다루고 있다면 그 페이지들은 그대로
남습니다). 다만 **이미 발표한 연말 리스트에 실린 글은 내릴 수 없습니다** — 리스트는 발표
시점 그대로 남아야 하기 때문입니다. 그런 경우는 요청해도 "리스트에 실려 있어 내릴 수 없다"는
답이 돌아옵니다.

## 2. 사용자(개발 담당)용

### 2.1 할 일 목록과 예상 시간

| 순서 | 할 일 | 예상 시간 |
|---|---|---|
| 1 | 비공개 GitHub 저장소 만들기 | 2분 |
| 2 | `tools/publish-desk/`의 내용물을 그 저장소 루트에 올리기 | 5분 |
| 3 | fine-grained PAT 발급, 시크릿 등록 | 5분 |
| 4 | 글 쓰는 분을 협력자로 초대 | 1분 |
| 5 | 테스트 이슈 하나로 첫 동작 확인 (커버 이미지 포함) | 10~15분 (빌드 대기 포함) |

### 2.2 비공개 저장소 만들기 + 트리 올리기

1. GitHub에서 새 저장소를 **Private**로 만듭니다. 이름은 자유입니다(예: `undernote-desk`).
2. 이 공개 저장소의 `tools/publish-desk/` **안의 내용물**을 그 저장소 루트에 복사해 커밋합니다
   (`.github/`, `scripts/`, `package.json`, `package-lock.json`, `.gitignore`, `README.md`).
   `docs/publishing.md`(이 파일)는 옮기지 않습니다.
3. 글 쓰는 분을 그 저장소에 **Collaborator**로 초대합니다 (Settings → Collaborators).

### 2.3 PAT 발급 — 정확히 이 권한만

**Fine-grained personal access token** (GitHub → Settings → Developer settings → Personal
access tokens → Fine-grained tokens)을 새로 만듭니다.

| 설정 | 값 | 왜 이것만인가 |
|---|---|---|
| Resource owner | 이 계정(fgda114) | |
| Repository access | **Only select repositories** → `undernote` (공개 저장소) 하나만 | 비공개 저장소는 이 토큰이 필요 없습니다 — 그건 Actions가 자기 자신의 기본 `GITHUB_TOKEN`으로 이미 접근합니다 |
| Repository permissions → Contents | **Read and write** | 공개 저장소를 체크아웃하고(읽기) 새 커밋을 푸시하려면(쓰기) 필요합니다 |
| Repository permissions → Metadata | Read (자동으로 켜짐) | fine-grained PAT의 필수 최소값 — 끌 수 없습니다 |
| 그 외 모든 권한 | **꺼진 채로 둡니다** | Issues·Pull requests·Actions 등은 이 토큰이 손댈 일이 없습니다 — 발행 워크플로는 이슈 댓글·닫기·라벨을 전부 **비공개 저장소 자신의** 기본 토큰으로 하고, 이 PAT은 공개 저장소 푸시에만 씁니다 |
| Expiration | 원하는 기간(만료되면 갱신 후 시크릿만 다시 등록하면 됩니다) | |

만든 토큰 값을 비공개 저장소의 **Settings → Secrets and variables → Actions → New repository
secret**에 이름 **`PUBLISH_PAT`**로 등록합니다 (워크플로가 정확히 이 이름을 읽습니다 —
`tools/publish-desk/.github/workflows/publish.yml`의 `secrets.PUBLISH_PAT`).

### 2.4 첫 동작 확인

1. 비공개 저장소에서 "새 글 쓰기 — 평론"으로 테스트 이슈를 하나 엽니다. 커버 이미지 칸에
   아무 사진이나 끌어다 놓아 보세요 — **이 부분이 미검증 지점입니다** (§3 참고), 실제로 되는지
   여기서 처음 확인하게 됩니다.
2. 비공개 저장소의 **Actions** 탭에서 `Publish` 워크플로가 도는 것을 지켜봅니다.
3. 성공하면: 이슈에 "발행됐습니다 + 주소" 댓글이 달리고, 이슈가 자동으로 닫히고,
   `published` 라벨이 붙습니다. 공개 저장소에 새 커밋이 하나 생깁니다.
4. 실패하면: Actions 탭의 로그에서 어느 단계가 실패했는지 봅니다. 이슈에도 (PD-* 또는 빌드
   실패 종류라면) 댓글이 달려 있을 겁니다 — §5 "고장 났을 때 볼 곳" 참고.
5. 테스트로 만든 글은 실제 사이트에 남지 않게 하려면, 공개 저장소에서 해당 파일들
   (`content/reviews/`, `content/albums/`, 새로 만들어진 `content/artists/`,
   `public/covers/`)을 지우는 커밋을 하나 더 올리세요.

### 2.5 라벨

이슈 템플릿(`review.yml`/`story.yml`)의 `labels:` 필드가 붙이는 `publish:review`·
`publish:story` 라벨은 **처음 쓰일 때 GitHub가 자동으로 만들어 줍니다** — 미리 만들 필요
없습니다. 발행 완료를 표시하는 `published` 라벨과 삭제(내림)를 트리거하는 `내림` 라벨은
`gh label create`(자동 생성이 안 되는 방식)를 쓰기 때문에, 워크플로 자체가 매 실행 시작에
"없으면 만들고, 있으면 넘어간다"로 두 라벨 모두 처리합니다 — 개발자가 따로 만들 일은 없습니다.

### 2.6 수정·삭제 (2026-09-08 추가)

발행 파이프라인은 세 가지 모드로 동작합니다 — `scripts/determine-mode.mjs`가 웹훅 이벤트
하나를 보고 판정합니다(테스트: `determine-mode.test.mjs`):

| 이벤트 | 조건 | 모드 |
|---|---|---|
| 이슈 열림 | (`published` 라벨은 아직 있을 수 없음) | **발행** — 기존과 동일 |
| 이슈 수정 저장 | `published` 라벨 없음 | **발행 재시도** (PD-* 오류를 고쳐서 다시 저장한 경우) |
| 이슈 수정 저장 | `published` 라벨 있음 | **수정** |
| `내림` 라벨 추가 | — | **삭제** |

**수정**(`scripts/publish.mjs#updateReview`/`updateStory`)이 고칠 수 있는 것은 본문·점수·커버
셋뿐입니다. 아티스트명·앨범명·장르·발매일(이야기는 제목)이 처음 발행 때와 다르면
`PD-IDENTITY-LOCKED`로 거절하고 무엇이 바뀌었는지 이슈에 답니다 — 파일은 아무것도 쓰지
않습니다. "처음 발행 때 값"은 별도 인덱스를 두지 않고 **공개 저장소 자신의 git 이력**에서
매번 다시 찾습니다(`scripts/resolve-published.mjs`) — 이 커밋 메시지 규약에 의존합니다:

- 최초 발행 커밋은 항상 두 문단 — 첫 줄 `발행: <제목>`, 빈 줄, 그다음 `Issue-Number: <N>`
- 이후 수정 커밋은 항상 첫 줄만 `수정: <제목>`로 바뀌고, `Issue-Number: <N>` 문단은 동일한 형태로 유지
- 커미터는 항상 `undernote publish desk` (이 워크플로 자신의 git identity)

이슈 번호가 제목과 **같은 줄에 있지 않고 별도 문단**인 것은 의도된 설계입니다(코드리뷰
MJ-1, 2026-09-09) — `<제목>`은 필자가 통제하는 텍스트라, 예전처럼 `(issue #N)`을 제목과
한 줄에 이어붙이면 필자가 우연히든 의도적이든 그 문자열을 제목에 그대로 적어 **다른
이슈의 조회에 낚일** 수 있었습니다(재현: throwaway repo에서 실제로 미끼 커밋이 선택됨).
`resolve-published.mjs`는 이제 `Issue-Number: <N>`를 줄 전체 앵커(`^Issue-Number: N$`)로만
찾고, GitHub 이슈 제목은 줄바꿈을 담을 수 없어 항상 첫 줄에만 있으므로, 제목이 이 문단과
겹칠 수 있는 경로 자체가 없습니다.

이 셋을 모두 만족하는 **가장 오래된** 커밋이 "원본"입니다. 이 규약이 깨지면(예: 커밋 메시지
형식을 손으로 바꾸면) 수정/삭제가 "발행 이력을 찾지 못했습니다"라는 인프라 오류로 실패합니다
— PD-* 취급이 아니라 개발자에게만 로그가 보이는 실패입니다(3.4절 참고). 이 조회가 커밋
이력을 훑어야 하므로, `public/` 체크아웃을 **`fetch-depth: 0`(전체 이력)**으로 바꿨습니다
— 기존의 얕은 클론(depth 1)보다 체크아웃 시간이 늘어납니다. §3.3의 실행 시간 실측은 이
변경 전 기준입니다 — 재측정 전까지는 늘어난 만큼을 실행 시간에 더해서 예상하세요.

**삭제**(`scripts/publish.mjs#takedownReview`/`takedownStory`)는 `내림` 라벨이 붙으면
동작합니다. 평론을 지울 때 그 앨범/아티스트 파일도 함께 지울지는 `scripts/takedown.mjs`가
결정합니다 — 다른 평론이나 이야기(`{ref}` 형태만, 자유 텍스트 언급은 제외 — E-113과 같은
규칙)가 여전히 그 앨범/아티스트를 참조하면 그 파일은 남깁니다. **확정 연말 스냅샷에 실린
평론은 삭제 전에 `lockedSnapshotYears`가 미리 걸러 `PD-TAKEDOWN-LOCKED`로 거절합니다** —
그대로 지웠다면 나중에 `E-110`(스냅샷 항목의 평론 실존) 빌드 실패로만 드러났을 문제입니다
(3.5절 참고).

**발행 시 파생되는 오류**: `publishReview`가 이번 실행에서 새로 만든 아티스트 파일이, 같은
실행의 다른 실패(예: 점수 형식 오류로 평론 파일 자체가 거부됨) 때문에 덩달아 고아
(`E-113`)로 잡히는 경우가 있습니다. `report-comment.mjs#suppressDerivedOrphan`이 — 이번
실행이 만든 아티스트에 대한 `E-113`이고, **같은 리포트에 다른 실패가 함께 있을 때만** — 그
줄을 빼고 필자에게 보여줍니다. 다른 아티스트의 `E-113`이나, 그 `E-113`이 유일한 실패인
경우는 절대 건드리지 않습니다(진짜 고아를 숨기지 않기 위한 조건 — 자세한 근거는 그 함수의
주석에 있습니다).

### 2.7 부제·태그 (2026-09-09 추가)

**부제**(`subtitle`, `src/lib/schema/album.ts`)는 앨범 스키마의 선택 필드입니다. 필드명을
`subtitle`로 정한 이유: 결정권자가 원한 지면 모양이 `제목 (부제)` 형태였고(`api-contracts`가
쓰는 일반적인 "타이틀 옆 짧은 수식어"라는 뜻의 영단어), `label`(장르 버킷이 이미 쓰는 이름)·
`description`(더 긴 글을 암시)과 겹치지 않게 골랐습니다. **평론 폼을 통해서는 새 앨범을 만들
때만 반영됩니다** — 이미 있는 앨범에 대한 후속 평론이 이 칸을 채워도 무시되고(참고 문구로
안내), "수정" 경로에서도 바꿀 수 없습니다(커버와 달리 부제는 아직 "나중에 채워도 된다"는
약속이 문서화된 적이 없어서, 범위를 좁게 잡았습니다 — 필요해지면 `updateReview`에
`resolveCoverForUpdate`와 같은 모양의 경로를 하나 더 추가하는 확장으로 열려 있습니다).
지면 렌더는 2차(프론트 담당)의 몫이지만, 파생 계층(`src/lib/derive/review-page.ts`의
`ReviewPageData#subtitle`)까지는 이미 값을 그대로 넘겨주도록 배선해 뒀습니다.

**태그**는 앨범·이야기 스키마에 이미 있었지만(`tags: string[]`) 폼에 칸이 없어 파일을 직접
고쳐야만 붙일 수 있었습니다 — 이번에 두 폼(평론·이야기) 모두에 선택 칸으로 추가했습니다.
`config/tags.yaml`은 `slug`(kebab-case)로 태그를 저장하지만 필자는 한글로 적으므로
(`resolve-content.mjs#resolveTags`)가 **등록부를 LABEL로 먼저 찾아** 이미 있는 태그(예:
"시티팝" → `city-pop`)는 그 slug를 재사용하고, 없는 태그는 `slugify.mjs`(ASCII만 남는 경우)
또는 `fallbackSlug('tag', …)`(전부 한글이라 ASCII가 하나도 안 남는 경우 — 결정적 해시 기반,
2026-09-08 "되묻지 않는다" 원칙과 동일)로 새 slug를 만듭니다.

**등록되지 않은 태그는 빌드를 실패시키지 않습니다** — `E-201`은 실패(E-1xx)가 아니라 경고
(E-2xx, `src/lib/checker/resolve.ts#checkTags`)이고, 미등록 태그도 자기 slug로 그대로
색인됩니다(`src/lib/derive/archive.ts`). 즉 폼에 칸이 없던 예전에도 필자가 파일을 직접 고쳐
태그를 붙이는 것 자체는 항상 가능했습니다. 그럼에도 **이 파이프라인은 새 태그를 매번
`config/tags.yaml`에 자동으로 등록합니다** — 실패를 막기 위해서가 아니라, 등록해 두지
않으면 그 태그가 영원히 "라벨 없는 slug"로만 남아(예: 한글 원문 없이 `tag-a1b2c3` 같은 해시
slug만 남음) 지면에 예쁜 한글 라벨을 못 붙이고, 매 빌드마다 같은 `E-201` 경고가 반복해서
뜨기 때문입니다. 태그는 앨범/아티스트 slug와 달리 **자기 자신의 URL을 이미 발행한 적이
없으므로**(등록부 항목을 나중에 손으로 고쳐도 깨지는 링크가 없습니다) 자동 등록의 위험이
0에 가깝다고 판단했습니다 — `config/tags.yaml`은 `tools/publish-desk`의 소유 경로이므로 이
판단을 그대로 구현했습니다(`frontmatter.mjs#appendTagEntries`). 같은 폼에서 같은 새 태그를
두 번 적어도(예: "시티팝, 시티팝") 등록부 항목은 하나만 생깁니다.

평론에서는 부제와 마찬가지로 **새 앨범을 만들 때만** 태그가 적용됩니다(이미 있는 앨범이면
무시 + 참고 문구). 이야기에서는 태그가 이야기 자신의 정체성(slug)과 무관하므로 "수정"
경로에서도 자유롭게 바꿀 수 있습니다 — "언급한 앨범들" 칸과 같은 취급입니다.

### 2.8 이야기 "언급한 앨범들" — 괄호 파싱 보정 (MN-3, 2026-09-09)

코드리뷰 MN-3: `resolveStoryAlbumLine`(`publish.mjs`)이 `앨범 이름 (아티스트 이름)`의 괄호를
무조건 "아티스트"로 해석했습니다 — 앨범명 자체에 괄호가 있고(예: "Songs (Deluxe Edition)")
필자가 아티스트를 생략하면, 그 괄호 안 문구("Deluxe Edition")가 아티스트 이름인 것처럼
이야기 지면의 AlbumBox에 표시됐습니다(`src/lib/derive/links.ts#deriveAlbumBoxRows`가
`artist`를 그대로 `meta`에 렌더합니다). 최악의 경우도 크래시나 발행 실패가 아니라
표시 오류였고(SS-9의 안전한 상태), Hananiah의 리팩토링 세션이 "고치면 동작이 바뀐다"는
이유로 권한 밖이라 에스컬레이션했습니다.

고친 방법: 괄호로 갈라낸 "아티스트" 후보가 **등록된 아티스트와 일치하지 않을 때**, 원문
그대로(괄호 포함)가 **이미 등록된 앨범의 제목과 정확히 일치하는지** 한 번 더 확인합니다.
일치하면 그 괄호가 제목의 일부라는 것이 데이터로 증명된 것이므로 통째로 `{text: 원문}`으로
씁니다. 일치하지 않으면(등록된 앨범도 아니고 등록된 아티스트도 아님) — 이야기 템플릿 자신의
placeholder("아직 평론 없는 어떤 앨범 (아직 모르는 아티스트)")가 보여주듯 **미등록 아티스트를
괄호로 적는 것은 의도된 정상 사용법**이라 데이터로 판별할 근거가 없으므로, 예전 동작을 그대로
유지합니다. 즉 이번 수정은 "등록된 앨범 제목에 괄호가 있는" 경우만 고치고, 미등록 앨범의
괄호 모호성은 여전히 남아 있습니다(해결 불가능한 자유 텍스트 모호성 — 안전한 상태로 남을
뿐입니다).

### 2.9 앨범 길이 (duration, 2026-09-09 추가)

**앨범 길이**(`duration`, `src/lib/schema/album.ts`)는 앨범 스키마의 선택 필드입니다.
결정권자가 기존 평론에 "52:26"을 넣고 싶어 한 요청에서 시작됐습니다 — 이 필드는 §2.7의
부제·태그와 똑같은 범위 결정을 따릅니다: **평론 폼을 통해서는 새 앨범을 만들 때만
반영됩니다**(이미 있는 앨범이면 무시 + 참고 문구), "수정" 경로에서도 바꿀 수 없습니다. 즉
이미 발행된 phoebe-bridgers-lost-weekend 같은 기존 앨범에 "52:26"을 넣으려면 이 폼을 거치지
않고 개발 담당이 `content/albums/<slug>.yaml`을 직접 고쳐야 합니다(이번 세션에서 실제로 그렇게
했습니다).

**형식 결정**: 필자가 적는 그대로("총 분:초", 예: "52:26")를 검증만 거쳐 그대로 저장합니다 —
초 단위 정수로 저장하고 표시할 때 다시 포맷하는 방식은 채택하지 않았습니다. 근거:

- `score`가 소수 float 대신 정확한 문자열로 저장되는 이유(YAML이 `8.30`을 `8.3`으로 접어버려
  검증이 불가능해지는 함정, `review.ts`의 자체 설명)와 같은 결의 판단입니다 — 이 프로젝트가
  이미 "정확한 문자열이 더 안전하다"고 결론 낸 전례를 그대로 따랐습니다.
- 초 단위 정수가 벌어줄 실익이 지금은 없습니다: 이 사이트는 오늘 길이로 정렬·비교·합산하는
  기능이 없습니다(트랙별 길이를 합산해 앨범 길이를 유도하는 기능은 트랙리스트라는 별도의,
  아직 결정되지 않은 기능입니다 — §"트랙 목록" 판단 참고). 실익 없는 파싱/재포맷 왕복만 늘리는
  선택은 피했습니다.
- "MM:SS"인지 "H:MM:SS"인지도 결정했습니다: **항상 총 분:초**입니다(예: 1시간이 넘는 앨범은
  "92:15"). "1:32:15"처럼 시:분:초로 나누는 형식은 거부합니다 — 필자가 시/분 자리올림을 직접
  계산할 필요가 없게 하기 위해서입니다(대부분의 트랙/앨범 메타데이터 도구가 이미 이렇게
  보여줍니다).
- YAML 함정 하나를 실제로 확인했습니다: `52:26`처럼 콜론이 들어간 값을 따옴표 없이 그대로 쓰면
  YAML 1.1의 60진수(sexagesimal) 정수 리터럴로 잘못 해석될 위험이 이론적으로 있습니다 — 이
  저장소가 실제로 쓰는 두 파서(`tools/publish-desk`의 `yaml` 패키지, Astro 콘텐츠 로더가 쓰는
  `js-yaml`) 양쪽 모두 직접 실행해 확인한 결과 둘 다 `52:26`을 그냥 문자열로 파싱합니다(60진수
  해석 없음) — 그래서 `score`처럼 따옴표를 강제할 필요는 없다고 판단했습니다(자세한 근거는
  `src/lib/schema/common.ts#durationSchema`의 주석).

지면 렌더는 2차(프론트 담당)의 몫이지만, 파생 계층(`src/lib/derive/review-page.ts`의
`ReviewPageData#duration`)까지는 이미 값을 그대로(재포맷 없이) 넘겨주도록 배선해 뒀습니다.
지면에 필요한 변경(SpecMeta.astro에 "Runtime" 행 추가 등)은 이 패키지의 소유 경로 밖이라
목록으로만 남겨둡니다 — `.agent-team/08-impl-notes/backend.md` 참고.

### 2.10 장르 폼·config 어긋남 자동 감지 (2026-09-09 추가)

**실제로 사람을 막은 사고입니다.** config/genres.yaml이 "Hip-Hop / R&B" 버킷 하나를 8개로
재편했는데(§참고 — 지금은 hiphop·rnb·digicore·rage·pop·indie-pop·rock·indie-folk),
`review.yml`의 장르 체크박스는 정적 텍스트라 그 순간 자동으로 안 바뀌고 옛 4개 그대로
남았습니다 — 결정권자가 Digicore·Rage 앨범에 실제 장르를 고를 수 없어 "그 외"만 남았고,
`resolveGenreBucket`은 "그 외"를 config 조회 없이 항상 통과시키므로(그 함수 자신의 주석)
`PD-GENRE-UNKNOWN`도 뜨지 않았습니다 — **빌드도, 발행 파이프라인도 이 사고를 스스로 발견하지
못했습니다.**

이 폼이 매 실행마다 GitHub에서 실시간으로 다시 렌더되는 게 아니라 커밋된 정적 텍스트라는
근본 원인은 고칠 수 없지만(§2.6 이전부터 review.yml 자체의 주석이 이미 이렇게 경고했습니다),
**어긋남 자체를 알아채는 것**은 가능합니다 — 발행 데스크가 매 실행마다 공개 저장소를
체크아웃하므로 `config/genres.yaml`을 항상 최신으로 읽을 수 있고, `review.yml`은 이 패키지
**자기 자신의** 파일이라 항상 같이 체크아웃돼 있기 때문입니다.

**한 만큼과 안 한 만큼을 분명히 합니다:**

- **한 것**: `resolve-content.mjs#missingGenreFormOptions`(+`allConfiguredGenreLabels`)가
  "config에는 있지만 폼 옵션에는 없는 라벨"을 계산하고, `publish.mjs#noteGenreFormDrift`가
  **새 앨범을 발행할 때마다**(기존 앨범 재사용 시에는 장르 자체를 건드리지 않으므로 검사하지
  않습니다) 이 계산을 실행해 어긋남이 있으면 이슈 댓글의 "참고" 항목에 자동으로 나열합니다 —
  발행 자체를 막지는 않습니다(이 검사가 오작동해도 발행이 실패해서는 안 되는, 순수한
  진단이라서입니다 — 템플릿을 못 읽거나 파싱에 실패해도 조용히 검사를 건너뜁니다).
- **하지 않은 것**: 폼 YAML 자체를 워크플로가 자동으로 다시 쓰는 것은 하지 않았습니다 — 팀장이
  직접 언급했듯 그건 "자기 저장소를 수정하는 것"이라 신중해야 하고, 매 실행마다 자기 자신의
  `.github/ISSUE_TEMPLATE/review.yml`을 커밋하는 워크플로는 이 프로젝트의 다른 어떤 자동화도
  하지 않는 새로운 종류의 위험(예: 그 커밋이 다음 실행의 트리거 조건과 겹치는지, 권한이
  맞는지)을 들여오므로 이번 범위에서는 제안만 하고 구현하지 않았습니다. 발행을 막지도
  않습니다 — 막았다면 이 진단 기능 자체의 버그가 정상적인 발행을 정지시킬 수 있어(위 "한
  것"의 마지막 문장과 같은 이유로), 진단은 항상 "알려주기"에서 멈추게 했습니다.
- **테스트 설계상 유의점**: `noteGenreFormDrift`의 템플릿 경로 인자는 **기본값이 없습니다**
  (`publishReview`도 마찬가지) — `main()`만 실제 `review.yml` 경로를 명시적으로 넘깁니다.
  이 패키지의 다른 모든 함수가 실제 경로를 가정하지 않고 항상 명시적으로 받는 것과 같은
  원칙(`resolve-content.mjs`의 모듈 설명)을 따른 것으로, 이 진단과 무관한 기존 테스트들이
  (자신만의 합성 `config/genres.yaml` 픽스처를 쓰면서) 이 패키지의 **실제** `review.yml`과
  우연히 비교되어 뜻하지 않게 깨지는 일을 막습니다.

## 3. 검증 못 한 것 — 정직하게

**아래는 실제로 확인하지 못했습니다. "될 것"이라는 근거는 있지만 "됐다"라고 쓰지 않습니다.**

### 3.1 비공개 저장소 첨부 이미지 다운로드 — 형태·호스트·인증 (전부 실측 완료, 2026-09-09)

**실측 갱신 (2026-09-09, `PD-COVER-NOT-IMAGE` 실패 리포트 — 결정권자가 실제로 사진을 끌어다
놓은 진짜 이슈, `fgda114/undernote-desk#2`)**: 이 절이 "미검증"이라고 적어뒀던 두 가지 중
**형태와 호스트는 이제 실측됐습니다** — 다만 실측이 답한 것은 아래에서 밝힌 딱 그만큼이고,
그 이상을 "확인됐다"고 넓혀 쓰지 않습니다.

- **형태**: GitHub은 마크다운(`![파일명](주소)`)이 아니라 **HTML `<img>` 태그**를 삽입했습니다
  (`<img width="640" height="640" alt="Image" src="..." />`). 이 프로젝트의 파서
  (`cover.mjs#extractImageUrl`)는 마크다운만 인식했으므로, 실제 커버 드래그앤드롭이 **매번**
  `PD-COVER-NOT-IMAGE`("사진이 아닌 내용")로 실패하는 상태였습니다 — 이번 커밋에서
  `<img>` 태그도 인식하도록 고쳤고(속성 순서·따옴표 종류·자기닫힘 여부 무관), 둘 다(마크다운도
  여전히) 받도록 했습니다 — GitHub이 어느 폼을 언제 다시 바꿀지 이 프로젝트가 통제할 수 없기
  때문입니다. 본문에 이미지가 여럿이면(마크다운·HTML 섞여도) **텍스트에서 먼저 나오는 것**을
  씁니다(뒤엣것을 조용히 버리는 것이 아니라 "첫 장" 규칙 — 커버 칸은 원래 한 장만 기대하는
  칸이라 실패보다 관대한 해석을 택했습니다).
- **호스트**: 실제로 쓰인 호스트는 `github.com`(정확히는
  `github.com/user-attachments/assets/<uuid>`)이었습니다 — 이 절 아래에 적힌 두 CANDIDATE
  (`user-images.githubusercontent.com`·`private-user-images.githubusercontent.com`) 어느 쪽도
  아니었습니다. UN-SEC-016 허용목록을 그 두 후보로 정확히 좁혔다면 **이 실제 URL이 그 자리에서
  거부됐을 것**입니다 — 즉 이번 실측은 "허용목록을 소유 도메인 전체(`github.com`·
  `githubusercontent.com`과 그 서브도메인) 단위로 잡고, 정확한 호스트가 확인될 때까지는 좁히지
  않는다"던 기존 판단이 옳았다는 근거입니다. **그래서 이번에도 허용목록을 좁히지 않기로
  했습니다** — 실제로 관찰된 호스트가 두 후보 CANDIDATE와도 다른 이상, "이제 안전하게 좁힐 수
  있다"는 근거가 아니라 오히려 "그 두 후보만으로는 부족했다"는 근거가 하나 더 늘어난 것이기
  때문입니다. `cover.test.mjs`에 이 정확한 호스트로 `downloadImage`를 통과시키는 테스트를
  추가해 회귀를 잡습니다.
- **인증 (2026-09-09 실측 갱신, `fgda114/undernote-desk#3`, `PD-COVER-FETCH-FAILED`)**:
  §2.4의 첫 실제 워크플로 실행에서 결정권자가 사진을 끌어다 놓았고, 파싱(위 두 항목)은
  성공했지만 다운로드가 **HTTP 404**로 실패했습니다. 이 절이 예전에 "경험적으로 알려진
  동작"이라며 근거로 댔던 가정 — 첨부 주소가 `?jwt=...` 형태의 자체 서명 토큰을 URL에 담고
  있어 인증 없이도 받아진다는 것 — 은 **틀렸습니다.** 실제 주소
  (`https://github.com/user-attachments/assets/<uuid>`)에는 그런 쿼리 파라미터가 없습니다.
  그 실제 주소로 직접 확인한 결과:

  | 요청 | 결과 |
  |---|---|
  | 인증 헤더 없음 | 404 |
  | `Authorization: Bearer <token>` | 200 · `image/jpeg` · 183,783 bytes |
  | `Authorization: token <token>` | 200 · 동일 |

  **비공개 저장소의 첨부는 인증이 필요합니다** — 공개 저장소 첨부(예:
  `user-images.githubusercontent.com`)는 이 문제가 없을 수 있다는 이전 관찰과 모순되지
  않습니다(그쪽은 애초에 미검증인 채로 남아 있었고, 이번 실측은 오직 **비공개** 저장소 첨부에
  대한 것입니다) — 그래서 `downloadImage()`의 토큰은 항상 선택값이고, 토큰이 없을 때의
  동작(인증 헤더를 아예 안 보냄)은 이번 수정 전과 정확히 같습니다.

  어느 토큰을 쓸지가 관건이었습니다. 워크플로에는 둘이 있습니다(§2.3):

  - **THIS(비공개) 저장소 자신의 기본 `GITHUB_TOKEN`** — 첨부가 이 저장소의 것이므로 이
    토큰이 맞습니다. `publish.yml`이 이미 `gh` CLI용으로 쓰고 있던 것과 같은 토큰이지만,
    "Resolve + write/update/delete content" 스텝에 `COVER_FETCH_TOKEN`이라는 **별도
    이름**으로 명시적으로 다시 넘깁니다 — `gh` CLI가 쓰는 `GH_TOKEN`과 이름을 분리해 둬야,
    나중에 `gh` 호출 쪽 인증 방식이 바뀌어도 커버 다운로드 쪽이 조용히 같이 바뀌는 일이
    없습니다.
  - `secrets.PUBLISH_PAT` — **공개 저장소 권한만** 있어 못 씁니다(§2.3의 최소 권한 분리를
    그대로 지킵니다). 이 저장소 자신의 첨부를 읽는 데는 애초에 유효하지 않은 토큰입니다.

  **리다이렉트 시 헤더 재판단**: `Authorization` 헤더는 오직 **맨 처음 요청한 호스트와 정확히
  같은 호스트**로 가는 요청에만 실립니다 — 매 리다이렉트 홉마다 다시 판단합니다
  (`cover.mjs#downloadImage`). UN-SEC-016의 호스트 허용목록(`github.com`·
  `githubusercontent.com` 및 서브도메인, SSRF 방어)과는 **다른, 더 좁은 규칙**입니다: 첫 홉
  (`github.com/user-attachments/assets/<uuid>`, 실제로 인증이 필요하다고 실측된 바로 그
  주소)은 토큰을 받고, 거기서 서명된 CDN 주소(예:
  `private-user-images.githubusercontent.com/...?sig=...`)로 리다이렉트되면 — 허용목록
  안이라도 — 토큰을 보내지 않습니다. 그 주소는 자기 쿼리스트링에 이미 자기 서명을 담고 있어
  이 프로젝트의 토큰이 필요 없고, curl이 교차 호스트 리다이렉트에서 기본적으로
  `Authorization`을 제거하는 것과 같은 이유(불필요한 자격 증명 유출 방지)로 보내지 않기로
  했습니다. 토큰 자체는 어떤 오류 메시지에도 로그에도 나타나지 않습니다
  (`cover.test.mjs`가 이 셋 — 첫 홉엔 실림·다른 호스트로는 안 실림·토큰 없으면 헤더 자체가
  없음 — 을 모두 검증합니다).
  - **401/403은 PD-COVER-FETCH-FAILED가 아닙니다**: 인증 거부는 필자가 사진을 다시
    올린다고 고쳐지는 문제가 아니라(이 워크플로 자신의 토큰이 없거나 만료됐거나 범위가
    부족한 것) — `CoverAuthError`로 구분해 던지고, `publish.mjs`는 이걸 잡지 않고
    그대로 흘려보내 다른 예상치 못한 오류들과 같은 "개발자만 보는 인프라 실패"로
    처리합니다(§"수정·삭제"의 PD-* vs 인프라 실패 구분과 동일).
  - **필자에게 보이는 오류 메시지도 고쳤습니다**: 원래 실패 메시지가 "HTTP 404"를 그대로
    노출했는데, 이제 404는 "사진이 지워졌거나 옮겨진 것 같습니다"로, 그 외 상태 코드는
    "서버 응답 코드 N"으로 표현합니다 — 어느 쪽도 개발자용 용어("HTTP")를 그대로 보여주지
    않습니다.
- **틀렸을 경우 어떻게 되는가**: 조용히 실패하지 않습니다. `downloadImage()`는 비-2xx 응답이나
  이미지가 아닌 content-type을 명시적으로 실패로 처리하고(`cover.test.mjs`가 이 부분을 실제로
  검증합니다), `publish.mjs`는 그걸 `PD-COVER-FETCH-FAILED`로 이슈에 그대로 알립니다. 즉
  **최악의 경우도 "커버 없이 발행됩니다" 정도가 아니라 "커버 이미지를 못 받았다고 명확히
  알려주고 발행을 멈춘다"**입니다 — §"본문 하이퍼링크" 절 판단과 같은 이유로, 이 지점에서
  실패를 감추기보다 멈추는 쪽을 택했습니다.
- **호스트 허용목록(UN-SEC-016, 보안 감사 · 2026-09-09 적용)**: `downloadImage()`는 이제
  `github.com`·`githubusercontent.com` 및 그 서브도메인이 아닌 호스트를 거부합니다(리다이렉트
  대상도 매 홉마다 다시 검사). 이 절 맨 위에 적었듯, **정확한 첨부 호스트를 실측하지 못한 채로
  내린 결정이었지만 이후 실측(위)이 이 판단을 뒷받침했습니다** — 위 두 후보
  (`user-images.githubusercontent.com`·`private-user-images.githubusercontent.com`)
  로 정확히 좁히면 SSRF 표면은 완전히 닫히지만, 실제 호스트가 조금이라도 다르면(예: GitHub이
  scheme을 바꿨거나 이 프로젝트가 문서화하지 못한 제3의 첨부 경로가 있다면) **이 기능이 실제로
  검증되는 첫 순간 자기파괴적으로 막힐 위험**이 있습니다. 그래서 "GitHub이 소유한 도메인 전체"
  단위로 허용 범위를 잡았습니다 — 공격자가 통제하는 임의 호스트나 클라우드 메타데이터 주소는
  이 두 도메인의 서브도메인이 절대 될 수 없으므로 이 판단이 막으려는 실제 위협(SSRF)은 그대로
  막히고, 위 미검증 리스크만 흡수합니다. 응답 크기 상한(10MB, Content-Length 사전 검사 +
  스트리밍 중단)도 같은 커밋에 함께 들어갔습니다.

### 3.2 Issue Form이 만드는 본문 형식이 안정적인 계약인가

`### <라벨>` 다음 줄에 값, 체크박스는 `- [X] <옵션>` — 이 형식은 GitHub의 공식 문서에 기술된
동작이고 여러 해째 바뀌지 않았지만, **이 세션에서 실제로 제출된 이슈로 검증하지 못했습니다**
(`scripts/fixtures/*.txt`는 그 문서화된 형식을 손으로 재현한 것입니다). §2.4의 첫 테스트
이슈가 이걸 실제로 검증하는 자리입니다 — 만약 파싱이 어긋나면(예: 라벨이 조금 다르게
렌더된다면) `parse-form.mjs`의 `extractField()` 정규식 하나만 고치면 되고, 그 아래
`resolve-content.mjs`·`frontmatter.mjs`·`publish.mjs`는 전혀 손댈 필요가 없습니다(레이어
경계가 의도한 대로라면).

### 3.3 GitHub Actions 사용량 — 비용

비공개 저장소의 GitHub Actions는 **공개 저장소와 달리 분당 과금 대상**입니다(플랜별 무료
한도를 넘으면). 이 프로젝트가 실측한 것은 `astro build` 자체의 시간뿐입니다
(`.agent-team/11-qa/latency-report.md` §3: 빌드(초) ≈ 11 + 0.81 × (평론 수+1) — 지금처럼
평론이 몇 편 안 될 때는 12~20초). **워크플로 전체 실행 시간(체크아웃 두 번 + `npm ci` 두 번 +
빌드 + 커밋/푸시)은 이 세션에서 실측하지 못했습니다** — `npm ci`가 `sharp`·`satori`·`resvg`
같은 네이티브 바이너리를 받는 부분이 가장 클 것으로 예상되지만 추정입니다. §2.4의 첫 실행이
Actions 탭에 실제 소요 시간을 남기니, 그때 실측치를 확인할 수 있습니다.

### 3.4 수정·삭제 파이프라인 — 실제 GitHub 실행으로 검증 못 함 (2026-09-08)

§1의 "나중에 고치고 싶을 때"·"글을 내리고 싶을 때"와 §2.6은 이 세션에서 **실제 GitHub
이슈로 한 번도 돌려보지 못했습니다.** 검증한 것과 안 한 것을 정직하게 나누면:

- **검증함**: `scripts/resolve-published.mjs`의 git 조회(원본 발행 커밋 찾기, 그 커밋 시점의
  앨범/아티스트 파일 내용 읽기)는 이 세션이 직접 `git init`으로 만든 진짜 저장소를 상대로
  실행해 확인했습니다(`resolve-published.test.mjs`) — 문자열을 흉내 낸 스텁이 아니라 진짜
  `git log --grep --all-match`·`git show <sha>:<path>` 호출입니다. `scripts/takedown.mjs`의
  삭제 대상 판정과 `scripts/publish.mjs`의 수정/삭제 오케스트레이션도 실제 파일 시스템(임시
  디렉터리) 상대로 end-to-end 검증했습니다(`publish.test.mjs`).
- **검증 못 함**: 실제 GitHub 이슈를 수정 저장했을 때 `issues: edited` 이벤트가 정확히 이
  워크플로가 가정한 모양으로 오는지, `내림` 라벨을 실제로 붙였을 때 `issues: labeled`
  이벤트의 `github.event.label.name`이 기대한 값을 담고 있는지는 **§3.2의 "Issue Form이
  만드는 본문 형식" 검증 못 함과 같은 종류의 공백**입니다 — §2.4의 첫 동작 확인을 발행뿐
  아니라 수정 1건·삭제 1건까지 실제로 돌려보는 것으로 확장해야 이 공백이 메워집니다.
- **틀렸을 경우 어떻게 되는가**: `determine-mode.mjs`가 예상 못 한 이벤트 모양을 받으면
  가장 보수적인 값(`'skip'`)으로 떨어지도록 짰습니다 — 아무 것도 안 하는 쪽으로 실패합니다
  (파일을 잘못 지우거나 잘못된 필드를 반영하는 쪽으로 실패하지 않습니다). `resolve-published.mjs`가
  원본 발행 커밋을 못 찾는 경우도 마찬가지로 "아무것도 안 함"(인프라 오류로 실패, PD-* 아님)
  쪽으로 떨어집니다.

## 4. 설계 판단 — 왜 이렇게 했는가

### 검증을 중복 구현하지 않았다

폼 값이 올바른지 판단하는 규칙(점수 형식, 슬러그 형식, 필수 필드 등)은 전부 공개 저장소의
`src/lib/schema/`·`src/lib/checker/`에 **이미** 있습니다. 이 파이프라인은 그 규칙을 다시 쓰지
않고, 공개 저장소를 체크아웃해 **그 저장소 자신의 `npm run build`**를 돌리는 것으로
검증합니다. 실패하면 그 빌드가 만든 `reports/build-report.md`를 거의 그대로 댓글로 답니다 —
그 메시지들은 이미 한국어로, "무엇이 잘못됐고 어떻게 고치는지" 형식으로 쓰여 있습니다
(`E-105: score ...`처럼). 새로 문장을 짓지 않고 그대로 전달하는 쪽이 두 벌의 규칙이 어긋날
위험보다 낫습니다.

이 원칙에서 벗어나는 유일한 지점은 `tools/publish-desk/scripts/slugify.mjs`와
`resolve-content.mjs`의 몇몇 정규식(SLUG_PATTERN 등)입니다 — 공개 저장소의 같은 이름 상수를
그대로 옮겨 적은 것으로, 각 파일 맨 위 주석에 "이건 사전 확인용이지 최종 판단이 아니다,
드리프트가 나도 최악의 경우 사전 확인 UX가 조금 틀릴 뿐 실제 게이트(빌드)는 여전히 지킨다"고
명시했습니다.

### 장르 드롭다운은 라벨 텍스트를, id는 실행 시점에 라이브 설정에서 찾는다

Issue Form 드롭다운은 정적 텍스트만 담을 수 있어 `config/genres.yaml`을 실시간으로 읽어오지
못합니다. 그래서 드롭다운 자체는 (`review.yml`에 손으로 적은) 고정 라벨 목록이지만, 그 라벨을
버킷 id로 바꾸는 일은 매 실행마다 **체크아웃한 공개 저장소의 실제 `config/genres.yaml`을 그
자리에서 읽어** 처리합니다(`resolve-content.mjs`의 `resolveGenreBucket`). 라벨 문자열이
어긋나면(장르 설정이 바뀌었는데 폼을 안 고쳤을 때) 조용히 아무 버킷이나 고르는 대신
`PD-GENRE-UNKNOWN`으로 멈추고 개발자에게 알립니다.

### 슬러그(URL 주소) — 앨범/아티스트는 실패하고 되묻는다, 이야기는 피해서 만든다

같은 이름의 아티스트/앨범이 이미 있으면 재사용하고(중복 파일을 만들지 않습니다), 새로
만들어야 하는데 이름이 전부 한글이라 인터넷 주소를 자동으로 만들 수 없으면 — **추측해서
만들지 않고** 영문 표기를 묻습니다(`PD-SLUG-EMPTY`). 이름/제목이 우연히 같은 슬러그로
충돌하면 — 다른 항목을 덮어쓰지 않도록 역시 멈추고 묻습니다(`PD-SLUG-COLLISION`). 이 두
경우는 데이터의 정체성에 관한 판단이라 사람에게 넘겼습니다.

반대로 이야기(음악 이야기) 제목이 우연히 겹치는 것은 의미 있는 충돌이 아니라서(같은 제목의
이야기 두 편이 있어도 전혀 문제가 아닙니다) `-2`, `-3`처럼 번호를 붙여 피합니다
(`firstAvailableSlug`) — 매번 되묻지 않습니다.

### 기존 앨범에는 새 커버를 얹지 않는다

평론 폼을 통해 **이미 있는 앨범**(예: 개발자가 `album-add.ts`로 먼저 만들어 둔 앨범)에 대한
평론을 낼 때 커버 이미지를 끌어다 놓아도, 기존 앨범 파일은 건드리지 않습니다. YAML 파일의 일부
필드만 안전하게 고쳐 쓰는 로직을 새로 만드는 대신, 이미 커버가 있으면 그게 우선이고 없으면
개발자가 손으로(또는 `album-add.ts` 재실행으로) 채우는 쪽을 택했습니다 — 이슈에는 "이번에 올린
커버 이미지는 반영되지 않았습니다"라는 참고 문구가 함께 달립니다.

### 발행일은 묻지 않는다

예전 방식(개발자가 대신 파일을 만들던 방식)에서는 평론·이야기의 `date:`를 사람이 적었지만, 이
파이프라인은 이슈가 성공적으로 처리된 시점(Asia/Seoul, KST)을 그대로 씁니다 — 물어볼 이유가
없는 값을 묻지 않는 쪽이 "원 노동 0"에 더 가깝다고 판단했습니다. 다르게 하고 싶다면(예: 실제
글을 쓴 날짜를 따로 받고 싶다면) `.github/ISSUE_TEMPLATE/*.yml`에 필드를 하나 추가하고
`parse-form.mjs`·`publish.mjs`에서 그 값을 쓰도록 한 줄 바꾸면 됩니다.

### MusicBrainz 자동 조회는 붙이지 않았다

`album-add.ts`(개발자용 CLI)는 아티스트/앨범 이름만으로 발매일·레이블·커버를 자동으로 찾아
줍니다. 이 파이프라인은 그렇게 하지 않고 발매일·장르를 폼에서 직접 받습니다 — 팀 리드가 전달한
필드 목록에 발매일이 이미 포함되어 있었고, GitHub Actions 안에서 외부 API 재시도·순위
매기기·대화형 확인 같은 것까지 다시 구현하면 신뢰성 위험(네트워크 실패 시 무엇을 해야 하는가)이
필요 이상으로 커진다고 판단했습니다. 나중에 원한다면 `resolve-content.mjs` 옆에
`src/lib/mb/client.ts`와 같은 방식의 조회 단계를 추가하는 확장은 가능합니다.

### 수정에서 "정체성 필드"는 왜 고칠 수 없는가 (2026-09-08)

아티스트명·앨범명·장르·발매일(이야기는 제목)은 slug/URL(`R-9`, exceptions.md — "발행된
콘텐츠의 slug는 바꾸지 않는다")이나 리스트 귀속(장르 버킷은 `R-8`, 발매 연도 설정에 결속)을
정하는 값입니다. 이 화면에서 바꾸는 걸 허용하면 이미 유통된 링크가 죽거나, 이미 도출된
리스트·아카이브가 조용히 다른 값으로 재분류될 수 있습니다 — 그래서 "발행 재개정"이 아니라
"발행 후에는 이 값들이 고정된다"는 원칙으로 정했습니다(결정권자 지시). 아티스트명·앨범명은
정확 일치가 아니라 `normalizeName`(공백/대소문자/유니코드 정규화)으로 비교합니다 —
발행할 때 이미 그 정규화로 "같은 아티스트/앨범"을 판단했던 것과 같은 기준을 그대로 씁니다.

**약점(정직하게 기록)**: "처음 값"은 최초 발행 커밋 시점의 git blob에서 읽습니다. 만약
개발자가 이 파이프라인을 거치지 않고 앨범/아티스트 파일을 직접 고치면(예: 오타 수정),
그 다음 수정 시도는 "고쳐지기 전의 옛 값"과 비교하게 되어, 실제로는 문제없는 저장인데도
"정체성이 바뀌었다"고 잘못 거절할 수 있습니다. 실패하는 방향이 "조용히 잘못 적용"이 아니라
"사람에게 되묻는" 쪽이라 안전하다고 보고, 별도의 두 번째(변경 가능한) 인덱스를 두지 않는
쪽을 택했습니다 — 두 번째 인덱스는 그 자체로 원본 git 이력과 어긋날 수 있는 새로운 위험입니다.

### 커버는 왜 수정 경로에서만 무조건 덮어쓰는가

§4의 "기존 앨범에는 새 커버를 얹지 않는다"는 **다른 앨범**(개발자가 먼저 만들었거나, 이미
다른 평론이 있는 앨범)에 대한 새 평론 제출이 우연히 커버 필드를 채웠을 때의 이야기입니다 —
그 커버가 누구 것인지, 왜 지금 있는 커버보다 나은지 판단할 근거가 없어 손대지 않습니다.
수정 경로는 다릅니다: 이 평론 **자기 자신의** 앨범을 고치는 것이므로 "남의 것을 덮어쓸" 위험이
구조적으로 없고, 오히려 "커버 없이 먼저 내고 나중에 넣어도 된다"는 폼 안내문의 약속을 지키려면
덮어쓰기가 되어야 합니다(팀 리드 지시). `updateAlbumCover`(frontmatter.mjs)는 `cover`·
`cover_source` 두 줄만 손으로 바꿔 쓰는 텍스트 편집입니다 — YAML을 통째로 파싱해서 다시
쓰지 않는 이유는, 그러면 이 패키지가 모델링하지 않는 필드(`album-add.ts`가 채우는 `mbid`·
`label`·`listen_links` 등)를 개발자가 나중에 손으로 채웠을 때 그걸 조용히 지워버릴 위험이
있기 때문입니다 — 자기가 안 쓰는 필드는 절대 건드리지 않는 것이 이 두 줄짜리 편집의
유일한 목적입니다.

### 삭제 — 무엇을 함께 지우는지는 archive.ts의 E-113 규칙을 그대로 흉내 낸다

`scripts/takedown.mjs`는 `src/lib/derive/archive.ts`의 `by_artist` 구성 규칙(평론의 앨범,
또는 이야기의 `{ref}` — 자유 텍스트 언급은 제외)을 그대로 다시 구현합니다. 두 저장소가
분리돼 있어 import로 공유할 수 없기 때문에 옮겨 적은 것이고(코드 상단 주석에 명시), 어긋나도
안전한 방향으로만 어긋납니다 — **덜 지우는 쪽으로 틀리면** 그 다음 실제 빌드의 `E-113`이
진짜로 잡아내고(고아 상태가 그대로 드러남), **더 지우는 쪽으로는 애초에 틀릴 수가 없습니다**
(이 모듈은 "아무것도 더는 참조하지 않을 때만" 지우자고 제안할 뿐입니다). 확정 연말 스냅샷에
실린 평론은 삭제 전에 `lockedSnapshotYears`가 먼저 걸러 `PD-TAKEDOWN-LOCKED`로 거절합니다 —
build의 `E-110`(스냅샷 항목의 평론 실존, `src/lib/checker/resolve.ts`)이 원래 이 경우를
잡지만, 그 실패는 "왜 안 되는지"를 필자가 읽을 말로 옮기기 어려운 자리라서 미리 잡습니다.
결정권자가 명시적으로 기각한 대안은 "빈 아티스트 페이지를 남기는 것"입니다 — `detectOrphans`
(`archive.ts`)가 "어떤 축에서도 도달 불가한 페이지"를 빌드 실패로 막는 규칙을 그대로 두는
쪽을 택했습니다.

### 이슈 번호 ↔ slug 대응은 별도 인덱스 없이 git 이력에서 매번 다시 찾는다

비공개 저장소(발행 데스크) 자신에 상태를 남기는 대신, 공개 저장소의 커밋 메시지
(`발행: <제목>` + 별도 문단 `Issue-Number: <N>`)를 유일한 진실로 삼았습니다
(`scripts/resolve-published.mjs`).
장점은 "쓰기 실패가 인덱스를 어긋나게 할 수 없다"는 것입니다 — 커밋이 실제로 푸시됐다면 그
사실 자체가 인덱스입니다. 대신 매번 `git log`/`git show`로 읽어야 하므로 `public/` 체크아웃을
전체 이력(`fetch-depth: 0`)으로 바꿔야 했습니다(§2.6·§3.4) — 별도 인덱스 파일을 뒀다면
얕은 클론을 유지할 수 있었겠지만, 그 인덱스 자신이 실패할 수 있는 새 지점이 됩니다. 이
트레이드오프는 이 세션의 판단이고, 실행 시간이 실제로 얼마나 늘었는지는 §3.3처럼 첫 실제
실행에서 확인해야 합니다.
