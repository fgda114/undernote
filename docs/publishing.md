# 발행 — 새 글을 사이트에 올리는 법

이 문서는 두 사람을 위해 쓰였습니다. 각자 자기 몫만 읽으면 됩니다.

- **글 쓰는 사람** — [바로 아래 §1](#1-글-쓰는-사람용)
- **개발 담당** — [§2](#2-사용자개발-담당용)부터

구현물은 `tools/publish-desk/`에 있습니다 (비공개 저장소에 그대로 올릴 파일 트리). 이 문서
자체는 이 공개 저장소에 남습니다.

---

## 1. 글 쓰는 사람용

### 평론을 쓸 때

1. 새 글 쓰기 화면을 엽니다 (개발 담당이 알려준 주소로 들어가면 "새 글 쓰기 — 평론"이라는 버튼이
   보입니다).
2. 아티스트 이름, 앨범 이름, 발매일, 장르, 점수를 적습니다. 발매일을 정확히 모르면 연도만
   적어도 됩니다.
3. "이 앨범, 안 들으면 손해라고 확신합니다" 체크를 합니다. **이 체크가 없으면 아무리 글이
   완성돼 있어도 올라가지 않습니다.**
4. 커버 사진이 있으면 그 칸에 파일을 끌어다 놓습니다. 없어도 됩니다 — 기본 이미지로 먼저
   나가고 나중에 넣어도 됩니다.
5. 본문을 씁니다. 마크다운을 몰라도 됩니다 — **문단을 나눌 때 그냥 Enter를 한 번 치면 됩니다.**
   맞춤법이나 띄어쓰기, 마침표는 고치지 않고 쓰신 그대로 나갑니다.
   - 특정 단어에 링크를 걸고 싶으면 `[이 곡](https://주소)` 처럼 대괄호 다음에 괄호로 주소를
     적으면 됩니다.
   - 문장을 `-`나 `#`, 숫자와 마침표(`1.`)로 시작하면 화면에서 목록이나 제목처럼 보일 수
     있습니다. 흔한 경우는 아니지만, 이상하게 나온 게 보이면 개발 담당에게 알려주세요.
6. 맨 아래 초록색 버튼을 누릅니다.

### 이야기를 쓸 때

제목과 본문만 있으면 됩니다. 글에서 다룬 앨범이 있으면 "언급한 앨범들" 칸에 한 줄에 하나씩,
`앨범 이름 (아티스트 이름)` 형식으로 적어주세요. 이미 평론이 있는 앨범이면 자동으로 링크가
걸리고, 아직 없어도 나중에 그 앨범 평론이 올라오면 자동으로 링크가 생깁니다 — 다시 손댈 필요
없습니다.

### 저장한 다음

- **문제가 없으면** 보통 몇 분 안에(길면 10분 정도) 실제 사이트에 올라갑니다.
- **뭔가 잘못 적으면** 사이트에 올라가지 않고, 이 화면에 댓글로 무엇이 잘못됐는지 알려드립니다.
  한국어로, 어느 칸이 문제인지 구체적으로 나옵니다 (예: "점수는 소수점 첫째 자리까지만 —
  8.35가 아니라 8.3 또는 8.4로 적으세요"). **그 칸만 고쳐서 저장하면 자동으로 다시 시도합니다**
  — 처음부터 새로 쓸 필요 없습니다.
- 새 아티스트나 새 앨범을 처음 다룰 때, 이름이 한글이면 "영문 표기를 알려달라"는 댓글이 달릴
  수 있습니다. 로마자로 한 번만 적어주면 됩니다(예: phoebe-bridgers) — 다음부터 같은
  아티스트를 다시 다룰 때는 안 물어봅니다.

## 2. 사용자(개발 담당)용

### 2.1 할 일 목록과 예상 시간

| 순서 | 할 일 | 예상 시간 |
|---|---|---|
| 1 | 비공개 GitHub 저장소 만들기 | 2분 |
| 2 | `tools/publish-desk/`의 내용물을 그 저장소 루트에 올리기 | 5분 |
| 3 | fine-grained PAT 발급, 시크릿 등록 | 5분 |
| 4 | 글 쓰는 분을 협력자로 초대 | 1분 |
| 5 | 테스트 이슈 하나로 첫 동작 확인 (커버 이미지 포함) | 10~15분 (빌드 대기 포함) |

### 2.2 비공개 저장소 만들기 + 트리 올리기

1. GitHub에서 새 저장소를 **Private**로 만듭니다. 이름은 자유입니다(예: `undernote-desk`).
2. 이 공개 저장소의 `tools/publish-desk/` **안의 내용물**을 그 저장소 루트에 복사해 커밋합니다
   (`.github/`, `scripts/`, `package.json`, `package-lock.json`, `.gitignore`, `README.md`).
   `docs/publishing.md`(이 파일)는 옮기지 않습니다.
3. 글 쓰는 분을 그 저장소에 **Collaborator**로 초대합니다 (Settings → Collaborators).

### 2.3 PAT 발급 — 정확히 이 권한만

**Fine-grained personal access token** (GitHub → Settings → Developer settings → Personal
access tokens → Fine-grained tokens)을 새로 만듭니다.

| 설정 | 값 | 왜 이것만인가 |
|---|---|---|
| Resource owner | 이 계정(fgda114) | |
| Repository access | **Only select repositories** → `undernote` (공개 저장소) 하나만 | 비공개 저장소는 이 토큰이 필요 없습니다 — 그건 Actions가 자기 자신의 기본 `GITHUB_TOKEN`으로 이미 접근합니다 |
| Repository permissions → Contents | **Read and write** | 공개 저장소를 체크아웃하고(읽기) 새 커밋을 푸시하려면(쓰기) 필요합니다 |
| Repository permissions → Metadata | Read (자동으로 켜짐) | fine-grained PAT의 필수 최소값 — 끌 수 없습니다 |
| 그 외 모든 권한 | **꺼진 채로 둡니다** | Issues·Pull requests·Actions 등은 이 토큰이 손댈 일이 없습니다 — 발행 워크플로는 이슈 댓글·닫기·라벨을 전부 **비공개 저장소 자신의** 기본 토큰으로 하고, 이 PAT은 공개 저장소 푸시에만 씁니다 |
| Expiration | 원하는 기간(만료되면 갱신 후 시크릿만 다시 등록하면 됩니다) | |

만든 토큰 값을 비공개 저장소의 **Settings → Secrets and variables → Actions → New repository
secret**에 이름 **`PUBLISH_PAT`**로 등록합니다 (워크플로가 정확히 이 이름을 읽습니다 —
`tools/publish-desk/.github/workflows/publish.yml`의 `secrets.PUBLISH_PAT`).

### 2.4 첫 동작 확인

1. 비공개 저장소에서 "새 글 쓰기 — 평론"으로 테스트 이슈를 하나 엽니다. 커버 이미지 칸에
   아무 사진이나 끌어다 놓아 보세요 — **이 부분이 미검증 지점입니다** (§3 참고), 실제로 되는지
   여기서 처음 확인하게 됩니다.
2. 비공개 저장소의 **Actions** 탭에서 `Publish` 워크플로가 도는 것을 지켜봅니다.
3. 성공하면: 이슈에 "발행됐습니다 + 주소" 댓글이 달리고, 이슈가 자동으로 닫히고,
   `published` 라벨이 붙습니다. 공개 저장소에 새 커밋이 하나 생깁니다.
4. 실패하면: Actions 탭의 로그에서 어느 단계가 실패했는지 봅니다. 이슈에도 (PD-* 또는 빌드
   실패 종류라면) 댓글이 달려 있을 겁니다 — §5 "고장 났을 때 볼 곳" 참고.
5. 테스트로 만든 글은 실제 사이트에 남지 않게 하려면, 공개 저장소에서 해당 파일들
   (`content/reviews/`, `content/albums/`, 새로 만들어진 `content/artists/`,
   `public/covers/`)을 지우는 커밋을 하나 더 올리세요.

### 2.5 라벨

이슈 템플릿(`review.yml`/`story.yml`)의 `labels:` 필드가 붙이는 `publish:review`·
`publish:story` 라벨은 **처음 쓰일 때 GitHub가 자동으로 만들어 줍니다** — 미리 만들 필요
없습니다. 발행 완료를 표시하는 `published` 라벨은 다른 메커니즘(`gh issue edit --add-label`)을
쓰기 때문에 자동 생성되지 않아서, 워크플로 자체가 매 실행 시작에 "없으면 만들고, 있으면
넘어간다"로 처리합니다 — 개발자가 따로 할 일은 없습니다.

## 3. 검증 못 한 것 — 정직하게

**아래는 실제로 확인하지 못했습니다. "될 것"이라는 근거는 있지만 "됐다"라고 쓰지 않습니다.**

### 3.1 비공개 저장소 첨부 이미지를 Action이 인증 없이 받을 수 있는가

GitHub Issue Form의 textarea에 이미지를 끌어다 놓으면 업로드되고
`![파일명](주소)` 형태의 마크다운이 삽입되는 것 자체는 모든 저장소(공개·비공개 무관)에서 되는
일반적인 GitHub 기능입니다. 이 프로젝트가 확신하지 못하는 것은 **그 주소를 워크플로가 로그인
없이(plain HTTP GET) 내려받을 수 있는가**입니다.

- 알려진 사실: 비공개 저장소의 첨부는 공개 저장소(`user-images.githubusercontent.com`)와 다른
  도메인(`private-user-images.githubusercontent.com`)에 저장되고, 그 이름 자체가 "이 주소는
  아무나 못 받는다"는 의도를 내비칩니다.
- 이 프로젝트가 가진 근거(경험적으로 알려진 동작이지 이 세션에서 직접 확인한 것은 아님): 그
  주소는 보통 `?jwt=...` 형태의 서명된 토큰을 URL 자체에 담고 있어서, **그 토큰이 유효한 동안은
  추가 로그인 없이도 그 주소 하나만으로 받아진다**는 것입니다. 맞다면 `cover.mjs`의
  `downloadImage()`가 지금 그대로 동작합니다.
- 이 세션에는 네트워크로 실제 GitHub 비공개 저장소를 만들어 이미지를 붙이고 받아보는 것이
  불가능했습니다(그런 저장소 자체가 아직 없습니다 — §2.4가 발행 파이프라인이 만들어진 뒤 처음
  이걸 확인하는 자리입니다).
- **틀렸을 경우 어떻게 되는가**: 조용히 실패하지 않습니다. `downloadImage()`는 비-2xx 응답이나
  이미지가 아닌 content-type을 명시적으로 실패로 처리하고(`cover.test.mjs`가 이 부분을 실제로
  검증합니다), `publish.mjs`는 그걸 `PD-COVER-FETCH-FAILED`로 이슈에 그대로 알립니다. 즉
  **최악의 경우도 "커버 없이 발행됩니다" 정도가 아니라 "커버 이미지를 못 받았다고 명확히
  알려주고 발행을 멈춘다"**입니다 — §"본문 하이퍼링크" 절 판단과 같은 이유로, 이 지점에서
  실패를 감추기보다 멈추는 쪽을 택했습니다.
- **만약 인증이 필요한 것으로 확인되면**: `cover.mjs`의 `downloadImage()`에 두 번째 시도로
  `Authorization` 헤더를 추가하는 것으로 고칠 수 있는 자리이지만, 어떤 토큰을 쓸 수 있는지(이
  PAT은 공개 저장소 권한만 있어 비공개 저장소 첨부에 못 쓸 가능성이 있습니다 — §2.3의 "최소
  권한" 원칙과 충돌합니다)는 이 세션에서 답할 수 없는 질문입니다. 필요해지면 별도로
  검토해야 합니다.

### 3.2 Issue Form이 만드는 본문 형식이 안정적인 계약인가

`### <라벨>` 다음 줄에 값, 체크박스는 `- [X] <옵션>` — 이 형식은 GitHub의 공식 문서에 기술된
동작이고 여러 해째 바뀌지 않았지만, **이 세션에서 실제로 제출된 이슈로 검증하지 못했습니다**
(`scripts/fixtures/*.txt`는 그 문서화된 형식을 손으로 재현한 것입니다). §2.4의 첫 테스트
이슈가 이걸 실제로 검증하는 자리입니다 — 만약 파싱이 어긋나면(예: 라벨이 조금 다르게
렌더된다면) `parse-form.mjs`의 `extractField()` 정규식 하나만 고치면 되고, 그 아래
`resolve-content.mjs`·`frontmatter.mjs`·`publish.mjs`는 전혀 손댈 필요가 없습니다(레이어
경계가 의도한 대로라면).

### 3.3 GitHub Actions 사용량 — 비용

비공개 저장소의 GitHub Actions는 **공개 저장소와 달리 분당 과금 대상**입니다(플랜별 무료
한도를 넘으면). 이 프로젝트가 실측한 것은 `astro build` 자체의 시간뿐입니다
(`.agent-team/11-qa/latency-report.md` §3: 빌드(초) ≈ 11 + 0.81 × (평론 수+1) — 지금처럼
평론이 몇 편 안 될 때는 12~20초). **워크플로 전체 실행 시간(체크아웃 두 번 + `npm ci` 두 번 +
빌드 + 커밋/푸시)은 이 세션에서 실측하지 못했습니다** — `npm ci`가 `sharp`·`satori`·`resvg`
같은 네이티브 바이너리를 받는 부분이 가장 클 것으로 예상되지만 추정입니다. §2.4의 첫 실행이
Actions 탭에 실제 소요 시간을 남기니, 그때 실측치를 확인할 수 있습니다.

## 4. 설계 판단 — 왜 이렇게 했는가

### 검증을 중복 구현하지 않았다

폼 값이 올바른지 판단하는 규칙(점수 형식, 슬러그 형식, 필수 필드 등)은 전부 공개 저장소의
`src/lib/schema/`·`src/lib/checker/`에 **이미** 있습니다. 이 파이프라인은 그 규칙을 다시 쓰지
않고, 공개 저장소를 체크아웃해 **그 저장소 자신의 `npm run build`**를 돌리는 것으로
검증합니다. 실패하면 그 빌드가 만든 `reports/build-report.md`를 거의 그대로 댓글로 답니다 —
그 메시지들은 이미 한국어로, "무엇이 잘못됐고 어떻게 고치는지" 형식으로 쓰여 있습니다
(`E-105: score ...`처럼). 새로 문장을 짓지 않고 그대로 전달하는 쪽이 두 벌의 규칙이 어긋날
위험보다 낫습니다.

이 원칙에서 벗어나는 유일한 지점은 `tools/publish-desk/scripts/slugify.mjs`와
`resolve-content.mjs`의 몇몇 정규식(SLUG_PATTERN 등)입니다 — 공개 저장소의 같은 이름 상수를
그대로 옮겨 적은 것으로, 각 파일 맨 위 주석에 "이건 사전 확인용이지 최종 판단이 아니다,
드리프트가 나도 최악의 경우 사전 확인 UX가 조금 틀릴 뿐 실제 게이트(빌드)는 여전히 지킨다"고
명시했습니다.

### 장르 드롭다운은 라벨 텍스트를, id는 실행 시점에 라이브 설정에서 찾는다

Issue Form 드롭다운은 정적 텍스트만 담을 수 있어 `config/genres.yaml`을 실시간으로 읽어오지
못합니다. 그래서 드롭다운 자체는 (`review.yml`에 손으로 적은) 고정 라벨 목록이지만, 그 라벨을
버킷 id로 바꾸는 일은 매 실행마다 **체크아웃한 공개 저장소의 실제 `config/genres.yaml`을 그
자리에서 읽어** 처리합니다(`resolve-content.mjs`의 `resolveGenreBucket`). 라벨 문자열이
어긋나면(장르 설정이 바뀌었는데 폼을 안 고쳤을 때) 조용히 아무 버킷이나 고르는 대신
`PD-GENRE-UNKNOWN`으로 멈추고 개발자에게 알립니다.

### 슬러그(URL 주소) — 앨범/아티스트는 실패하고 되묻는다, 이야기는 피해서 만든다

같은 이름의 아티스트/앨범이 이미 있으면 재사용하고(중복 파일을 만들지 않습니다), 새로
만들어야 하는데 이름이 전부 한글이라 인터넷 주소를 자동으로 만들 수 없으면 — **추측해서
만들지 않고** 영문 표기를 묻습니다(`PD-SLUG-EMPTY`). 이름/제목이 우연히 같은 슬러그로
충돌하면 — 다른 항목을 덮어쓰지 않도록 역시 멈추고 묻습니다(`PD-SLUG-COLLISION`). 이 두
경우는 데이터의 정체성에 관한 판단이라 사람에게 넘겼습니다.

반대로 이야기(음악 이야기) 제목이 우연히 겹치는 것은 의미 있는 충돌이 아니라서(같은 제목의
이야기 두 편이 있어도 전혀 문제가 아닙니다) `-2`, `-3`처럼 번호를 붙여 피합니다
(`firstAvailableSlug`) — 매번 되묻지 않습니다.

### 기존 앨범에는 새 커버를 얹지 않는다

평론 폼을 통해 **이미 있는 앨범**(예: 개발자가 `album-add.ts`로 먼저 만들어 둔 앨범)에 대한
평론을 낼 때 커버 이미지를 끌어다 놓아도, 기존 앨범 파일은 건드리지 않습니다. YAML 파일의 일부
필드만 안전하게 고쳐 쓰는 로직을 새로 만드는 대신, 이미 커버가 있으면 그게 우선이고 없으면
개발자가 손으로(또는 `album-add.ts` 재실행으로) 채우는 쪽을 택했습니다 — 이슈에는 "이번에 올린
커버 이미지는 반영되지 않았습니다"라는 참고 문구가 함께 달립니다.

### 발행일은 묻지 않는다

예전 방식(개발자가 대신 파일을 만들던 방식)에서는 평론·이야기의 `date:`를 사람이 적었지만, 이
파이프라인은 이슈가 성공적으로 처리된 시점(Asia/Seoul, KST)을 그대로 씁니다 — 물어볼 이유가
없는 값을 묻지 않는 쪽이 "원 노동 0"에 더 가깝다고 판단했습니다. 다르게 하고 싶다면(예: 실제
글을 쓴 날짜를 따로 받고 싶다면) `.github/ISSUE_TEMPLATE/*.yml`에 필드를 하나 추가하고
`parse-form.mjs`·`publish.mjs`에서 그 값을 쓰도록 한 줄 바꾸면 됩니다.

### MusicBrainz 자동 조회는 붙이지 않았다

`album-add.ts`(개발자용 CLI)는 아티스트/앨범 이름만으로 발매일·레이블·커버를 자동으로 찾아
줍니다. 이 파이프라인은 그렇게 하지 않고 발매일·장르를 폼에서 직접 받습니다 — 팀 리드가 전달한
필드 목록에 발매일이 이미 포함되어 있었고, GitHub Actions 안에서 외부 API 재시도·순위
매기기·대화형 확인 같은 것까지 다시 구현하면 신뢰성 위험(네트워크 실패 시 무엇을 해야 하는가)이
필요 이상으로 커진다고 판단했습니다. 나중에 원한다면 `resolve-content.mjs` 옆에
`src/lib/mb/client.ts`와 같은 방식의 조회 단계를 추가하는 확장은 가능합니다.
